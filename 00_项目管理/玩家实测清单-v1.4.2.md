## 一、甲组 · 不需要打仗（10 项）

### 甲-1 ｜改声望 → 读档生效（§11.1-8）
在**战役地图**状态的存档（`barbarossa-Conference3-2.usg`）上，概览页把声望改成一个明显的数
（如 `999`）→ 应用更改 → **进游戏读档** → 看战役界面的声望。
✅ 期望：声望是你改的那个数。

### 甲-2 ｜加一张卡 → 卡牌数 +1（§11.1-9）
手牌页 → 加一张卡（选一个卡种）→ 应用更改 → 读档 → 数战役界面的牌。
✅ 期望：比改之前多 1 张。

### 甲-3 ｜改商店价格 → 读档生效（§11.1-10）
商店页 → 改某条目价格 → 应用更改 → 读档 → 看商店里那个商品的价格。
✅ 期望：价格变了。

### 甲-4 ｜价格改成 0 → 显示「免费」而不是下架（§11.1-12）
同甲-3，把价格改成 **0** → 读档 → 看商店。
✅ 期望：商品**还在列表里**，标成**免费**（不是消失）。

### 甲-5 ｜删掉一个商店条目 → 下架（§11.1-14）
商店页 → 删掉某个条目 → 应用更改 → 读档 → 看商店。
✅ 期望：这个商品**从列表里消失**。

### 甲-6 ｜改单位显示名 → 游戏里显示中文名，且不用重启游戏（§11.1-7）
单位明细页 → 把某个单位的显示名改成「我的部队」→ 应用更改 → **进游戏读档**（不重启游戏）。
✅ 期望：游戏里这个单位显示「我的部队」。

### 甲-7 ｜改 HQ 兵库数量 → 界面看到新存量；**进战斗后仍然生效**（§11.1-21 + §11.7-1）
总部页 → 兵库某条数量改成明显的数（如 `10`）→ 应用更改 → 读档 → 看会议/商店界面的存量。
然后**进一场仗**，再看这个总部还有没有那些部队。
✅ 期望：读档后存量变了；**进战斗后没被清掉**。

### 甲-8 ｜战役开局·第一次会议：能打开、不崩、改得动（§11.2-1）
打开 `Stalingrad-Conference1.usg`（战役开局，没有单位）。
✅ 期望：① 正常打开，单位列表显示「无单位（战役开局）」而不是报错/崩；
② 改声望、改卡牌、改商店都能提交成功。

### 甲-9 ｜独立场景：能打开、能改、能存（§11.2-6）
打开 `games\west_overlord.usg` → 改一个单位的经验 → 应用更改。
✅ 期望：保存成功，改动在。

### 甲-10 ｜「有 last_conference、无 last_game」的盲区存档：不崩、能力判断正确（§11.3-4）
打开 `west-Conference2-1.usg`（这类存档本机有 5 个）。
✅ 期望：不报错、不崩；该能改的能改、该禁用的禁用（而不是反过来）。

## 二、乙组 · 需要打一场仗（8 项）

> 这组是**最值钱**的一组（§11.2c「重组机制」整组至今没有自动化测试）。
> 用 `tester-overlord.usg`（overlord）或 `tester-cards.usg`（4th_monte_cassino）。
> **改完先「应用更改」，再进游戏读档**，看值有没有生效。

### 乙-1 ｜战斗中改参战单位 → 战斗内立刻生效（§11.2-2 / §11.2b-1 / §11.2c-1）
在战斗中的存档里，改一个**正在参战**的单位：经验、显示名、战力（act_st）、挂一个特种兵。
✅ 期望：读档进战斗后，**四项全部生效**，不用重开。

### 乙-2 ｜改「场景初始单位」的 sup_st → 进战斗后 sup_st 变 0、act_st 相应增加（§11.2c-4）
找一个**不在当前战斗、但属于本场景初始单位**的单位（战役地图页单位列表里可分辨），
把它的 `sup_st`（被压制/待部署步数）改成 `3` → 应用更改 → 进战斗。
✅ 期望：进战斗后这个单位 `sup_st` 变成 0，`act_st` 相应增加。

### 乙-3 ｜把某个特种兵的「被压制」打开 → 进战斗后被重新激活（§11.2c-5）
单位明细页 → 把某个已挂特种兵的 `active` 关掉（压制）→ 应用更改 → 进战斗。
✅ 期望：进战斗后这个特种兵**又变成活跃**（游戏重新对账）。

### 乙-4 ｜登陆单位（资产 5，`lci`）四个子步（§11.2c-6）
找到那个登陆单位（overlord / 4th_monte_cassino 里都有），逐条测：
1. 它的 `act_st + sup_st` **本来就等于 6**；
2. 把 `act_st` 改成 `2` → 进战斗 → **被补回 6**；
3. 把 `act_st` 改成 `9` → 进战斗 → **保持 9**（只增不减）；
4. 给它加一个**场景目标里没有**的特种兵 → 进战斗 → **那个特种兵消失**（退回总部兵库）。

### 乙-5 ｜空降单位（资产 3，`para_plane`）→ 加任何 spec 都清空（§11.2c-7）
找到空降单位 → 给它挂一个特种兵 → 应用更改 → 进战斗。
✅ 期望：进战斗后这个单位 **specs 全空**。

### 乙-6 ｜早期增援 / 无登陆资产场景的增援单位（§11.2c-8 / §11.2c-9）
* 早期增援单位（`on_turn=4` 那种）→ 进战斗 → 按游戏的 lci 规则对账；
* **没有登陆资产**的场景（`has_ppas=False`）里的增援单位 → **不**走 lci 对账。
> ⚠️ 这两条在游戏里不好直接观察 —— **能看出明显不对就报给我**（单位凭空消失/属性被改），看不出就跳过。

### 乙-7 ｜改战区资产 → 读档进战斗后生效（§11.1-22 + §11.7-5）
战斗中的存档 → 战区资产页 → 改某项的可用次数（如空袭次数）→ 应用更改 → 读档进战斗。
✅ 期望：进战斗后那个资产**次数是你改的值**。

### 乙-8 ｜重置会议**撤不掉**战区资产，但修改器的「撤销」能撤掉（§11.7-7）
接着乙-7：改完战区资产后，**在游戏里点「重置会议」** → 再读档看战区资产。
然后回到修改器点「撤销」。
✅ 期望：① 重置会议后战区资产**还在**（游戏内回退撤不掉它，这是预期的）；
② 修改器的「撤销」能把它撤掉。

## 三、丙组 · 回退与撤销（4 项）

### 丙-1 ｜「重置会议」→ 根级修改整体消失，且没有「一半新一半旧」（§11.1-15 / §11.5-9）
在**战役地图**状态存档上改点根级的东西（声望 + 一个单位的经验）→ 应用更改 →
进游戏点「重置会议」→ 回修改器重新打开存档。
✅ 期望：两处改动**都回到改前**；不是只回退一半。

### 丙-2 ｜读档继续战斗 → 改动仍在（§11.1-16）
改根级内容 → 应用更改 → 进游戏**读档继续战斗** → 回修改器看。
✅ 期望：改动**还在**（读档不重算）。

### 丙-3 ｜「重打上一场」→ 对 last_game 的修改消失（§11.3-3）
改根级内容 → 应用更改 → 进游戏点「重打上一场」→ 回修改器看。
✅ 期望：改动**消失**（被游戏自己的回退撤销，**这是预期行为**，不是 bug）。

### 丙-4 ｜撤销栈的四件事（§11.6-3 / §11.6-4 / §11.6-5 / §11.6-6）
1. 改一次 → 应用更改 → 点「撤销」→ **精确回到这次修改前**（不是回到最初）；
2. 一次改 **3 个单位** → 应用更改 → 点一次「撤销」→ **三个一起退回**；
3. 点「撤销」后**关掉程序重开** → 「撤销」按钮**仍然可用**；
4. 先改一次 → **在游戏里手动改同一个存档** → 回修改器点「撤销」→
   ✅ 期望：修改器**拒绝执行并明确提示**（提示里应有「基准」字样），**不是硬改回去**。

## 四、这些**不用你测**—— 我已核实（结论）

| 事项 | 我的核实结论 |
|---|---|
| §11.4-1 / §11.4-9「`games/<场景>/units.yml` 两种格式」 | **不是缺陷**。实测 73 个存档：**当前战斗层**的 `units.yml` **19/19 全是 `list[int]`**；`list[dict]` 只出现在**已结束**的战斗层，而修改器根本不读那一层（`battle_dir()` 只指当前场景，`container.py:626`）⇒ 只认 int 是对的。 |
| §11.4-9「不缓存上一份判断」 | **正确**。每次接口都是 `with open_save(...)` 新建实例（`server.py:439/795/1939/1972`）⇒ 缓存不跨存档、不跨请求。 |
| §11.2b-4「改已阵亡单位」 | **不会污染存档**。不在根表里的 id 会明确报错「存档里没有 id 为 X 的单位」并**不写盘**（`handlers.py:509` 等 6 处）。⚠️ 规范写的是「跳过不报错」，实现是「报错拒绝」—— 行为更安全，只是文案口径不同。 |
| §11.2b-5 / §11.4-7「enroute_units」 | 存档里的 `games/<场景>/enroute_units.yml` **不被修改器读取**（`enroute_units` 只在 `campaigns.py:411` 从**游戏包**场景数据读）⇒ 「能解析」不成立；但**也不会被误改**（写盘白名单里 `games/**` 除当前战斗 `main.yml`、`cities/forts`、`hqs.yml` 外全只读）。 |
| §11.5-3「代码里没有写 document/ 的路径」 | **条目文字过期**：§7.2 W9 明确允许 `document/units.yml`、`document/hqs.yml`、各场景名册/战斗层 `hqs.yml` 与废墟快照两张表（U148/U184 放宽后没同步条目）。运行时白名单有测试守着。 |
| §11.2c-2 / §11.2b-3「改 `uv`」 | 核心库**有意不给改 `uv`**（`handlers.py:42-48`「没把握就不给，宁可不写也不写坏」），测试还断言它必须被拦 ⇒ 条目与实现方向相反。 |
| §11.2-7「已结束战斗的单位只读展示」 | 核心库**没有这个视图**（没有「历史战斗单位」API）⇒ 是**功能缺失**，不是解析问题。**要不要做**见 §五。 |
| §11.2c-3 / §11.2c-10 / §11.2c-11「重组预警 / 算出会被重组的单位」 | 代码里**没有这套东西**（`src` 里搜不到「重组」相关实现）⇒ 同样不是测试项，见 §五。 |
