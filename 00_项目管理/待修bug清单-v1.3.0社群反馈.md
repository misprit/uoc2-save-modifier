## 二、批次一：数据正确性（会写坏存档 / 直接报错）

### B-1 商店「删一条再添同一个」必然报重复条目、整批无法应用

* **社区原话**：「删除条目再重新添加会报告不能出现重复条目而无法应用，这个是老问题。」
* **根因**：`src/save_modifier_core/plan.py:277-292` 的 `order_edits()` 把**按下标删除**的编辑排到最后
  ⇒ `store_add` 落在 `others` 里**先执行** ⇒ 此时旧条目还在列表里 ⇒ 撞上 `handlers.py:2021-2032`
  的重复条目校验 ⇒ 整批 plan 失败。
  排序规则本是为解决「删除导致下标漂移」（U35/U91/U121），**没考虑「删了再加同一个」**。
* **实测**：`plan.ok = False`，错误「caucasus/store 里已经有「装备 infantry（german）」了」，
  `order_edits` 输出 `['store_add', 'store_remove']`。
* **修法方向**：`store_add` 遇到与待删条目 identity 相同的目标时，应识别为「替换」而非「重复」；
  或把 `store_add` 排到同组的 `store_remove` **之后**。
* **验收**：删一条 → 重新添加同一条 → 应用成功，且存档里**只有一条**该商品。
* **状态**：✅ 已修 —— 提交 `0aae9b3`

### B-2 兵库「新增兵力」的国籍/兵种下拉不生效，界面显示 `this value`

* **社区原话**：「兵库新增兵力窗口依然无法选择具体国籍和兵种。并且国籍依旧为 ''this value''。该功能当前仍不可用。」
* **根因**：`src/save_modifier_web/web/index.html:4323` 与 `:4327` 写成
  `onchange="hqPoolEquip('{0}','this.value')"` —— **引号把 `this.value` 变成了字面字符串**，
  于是无论选哪个国籍，传给 `hqPoolEquip` 的都是字面量 `"this.value"`。
  同文件 `:2007`（`setUnitAp(${u.id},this.value)`）、`:2361`、`:4528` 都是**正确**的无引号写法 ⇒ 纯手误。
* **证据**：`this value` 在**全仓库、游戏数据 yml、玩家存档里均零命中** ⇒ 确认是运行时产生的。
* **修法方向**：去掉那对多余引号，改成 `onchange="hqPoolEquip('{0}',this.value)"`。
* **验收**：兵库新增窗口选国籍后，`MODAL.equipNat` 变成真实国籍 id；界面不再出现 `this value`。
* **状态**：✅ 已修 —— 提交 `823160b`

### B-3 总部等级调整后界面不同步（显示升级了，再调压制却按旧等级算）

* **社区原话**：「调整等级之后界面没正确更新。虽然显示升级了，但再调节压制会发现还是原本的等级，但最终应用后会发现修改结果是正确的。」

* **状态**：✅ 已修 —— 提交 `e7502f3`

### B-4 单位经验上限应为 399（当前允许改到 400）

* **社区原话**：「单位经验上限是399而非400，修改上限要改，不然会出错。」
* **根因（游戏字节码实证）**：`lib/uoc2/state/entities/unit.pyc` 的 `add_xp` 反汇编为
  `self.xp = min(self.xp + xp, 399)` ⇒ **游戏自己的经验上限是 399**。
  存档 schema 的 `Range(min=0, max=400)`（`data_validation/unit.pyc`）只是**校验**上限（不拒绝 400），
  **逻辑**封顶 399 ⇒ 填 400 读档不报错，但**任何一次经验结算都会被立刻拉回 399**。
* **当前代码**：`handlers.py:63` `"xp": (0, 400)`；`plan.py:377-379` 校验 `0 <= xp <= 400`；
  `index.html:2468` `bindNumIn(..., max:400)`；i18n 词表 `范围 0 – 400（schema 硬范围）`。
* **修法方向**：三处上限改 399；i18n 词条同步（措辞要改成「游戏逻辑上限 399」，不要再写 schema 硬范围）。
* **验收**：经验输入框最大 399；核心库拒绝 400 并给出 0..399 的提示。
* **状态**：✅ 已修 —— 提交 `64c3c45`

### B-7 切换战役存档后战役页大面积串数据

* **社区原话**：「切换读取不同战役的存档时战役界面的部分信息不更新。包括路线图（只有标题更新）、废墟（能够识别出不是当前场景，界面显示可以修改，应用更改时无法生效）、场景名册（除了标题正确，其他都串了）」。

* **附带同源问题**：写盘 / 撤销后 `openSave()` 也不会重取 `CDETAIL` ⇒ 修完废墟后清单仍旧。
* **修法方向**：切换存档 / 写盘 / 撤销后清 `CDETAIL` 并重取；`CDETAIL` 应带存档 id 校验。
* **验收**：切换两个不同战役存档，路线图 / 废墟 / 场景名册三块都随之更新。

* **社区原话**：「放弃存档当前改动重新读取的功能似乎没有生效？」

  **没有清 `PENDING`**；对比 `doSwitchSaveForce`（`:5056-5057`）**有** `PENDING = []; paintPending();`。

* **验收**：改几处 → 「重新读取」→ 底栏待应用数归零。

### B-11 商店下架全部后无法再新增，误显示「没有商店数据」

## 五、结案项（拍板：不是 bug，回复社区时说明原因）

### N-1 总部改名会连带改缩写 —— **有意设计**

* **依据**：`handlers.py:368-392` `_rename_fields()` 明确同时改 `name_brief` + `name_super_brief`，
  依据是游戏 `campaign_ctrl._hq_bar_button` 读的就是 `name_super_brief`
  ⇒ 不一起改，战役地图顶上那个 HQ 标签会变**空**。
* **回复口径**：这是刻意的 —— 简称是另一个独立字段，游戏多处读它；只改显示名会造成「有的地方变、有的地方空」。

### N-2 兵库 / 商店特种兵「显示全部」排序乱 —— **排序已实现，真实原因是折叠 + 无搜索**

* **事实**：`index.html:1776-1801` 的 `specNatGroups()` 已实现三层排序：
  阵营分带（本方最前）→ 国籍分组（按本方可挂数降序 + 中文名）→ 组内按**中文名**排。
* **社区感到「乱」的真实原因**：① 国籍组**默认折叠**；② **单位明细页没有搜索框**
  （商店/兵库模态有搜索，`:4206-4227`）⇒ 375 种只能逐组翻。
* **附带发现（文档漂移）**：`index.html:1773` 的注释还写着「直接用目录表的原始顺序 ⇒ 看起来乱」，
  **与实现矛盾** ⇒ 需修注释（属知识性错误）。
* **回复口径**：排序本身是按中文名的；卡在分组默认折叠与该页缺搜索。已记录为改进项。

### N-3 手牌不能加伞兵卡 —— **U187 的有意保守兜底**

* **事实**：`handlers.py:1479-1498` 硬拦所有 `has_unit` 类卡（空降/登陆/伞兵/师级空降）；
  界面置灰并给原因（`index.html:4389-4393`，词表 `:783`）；有测试 `tests/test_card_hand_summon_ban.py:152-161`。
* **⚠️ 重要**：这**不是根因修复** —— 崩溃点至今未定位（`docs/证据脚本/e169_card_summon.py` 实测：
  游戏自己的存档里也有同样形态的召唤卡 ⇒「重复召唤 ⇒ 崩溃」**未被证实**）。
* **回复口径**：手牌侧的召唤卡暂时整类禁用（保守兜底）；卡牌商店侧已单独加同类型去重（B-5）。

### N-4 单位经验上限 399 —— **已转为 bug B-4**（原判定被推翻）

* **原判定**（曾写「不是 bug」）：schema 是 `Range(min=0, max=400)` 含边界 ⇒ 400 合法。
* **推翻依据（游戏字节码）**：`lib/uoc2/state/entities/unit.pyc` 的 `add_xp` 反汇编为
  `self.xp = min(self.xp + xp, 399)` ⇒ **游戏逻辑上限是 399**；schema 的 400 只是校验上限。
* 用户拍板：改成 399。⇒ 转入批次一 B-4。

### N-5 卡牌 `used` 字段开放 —— **已批准（并入批次二）**

* **社区原话**：「对可持续的卡牌应该有修改是否已经使用的功能。」
* **字节码实证**：`lib/uoc2/state/game/actions/card.pyc` 的 `_apply_card_deck` 读 `persistent` 与 `used`：
  persistent 卡用过后 `used = True` 且**留在牌堆**；非 persistent 卡用过后从战役移除。
  ⇒ `used` 语义明确 = 「这张牌已经用过」。
* **拍板**：**开放**，但**仅对 persistent 卡**；非 persistent 卡不给改（用完即移除，改了无意义）。
* **当前实现**：`handlers.py:81-82` `CARD_FIELD_ALLOWED = {"is_free"}`；改 `used` 会被拒（`:1563-1566`）。
* **待做**：加 `used` 到白名单（仅 persistent 卡）+ 界面加开关 + i18n。
