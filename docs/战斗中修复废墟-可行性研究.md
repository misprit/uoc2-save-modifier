# 战斗中修复废墟 —— 可行性研究（2026-11-27）

> **问题**（玩家）：「玩家在战斗中不小心造成了废墟需要立即修复」——
> 现在修改器在战斗中**禁止**修废墟（`handlers._city_restore` 里
> `w.require(not w.caps.in_battle, ...)`）。这个限制能不能去掉？
>
> **取证脚本**：`docs/证据脚本/e170_battle_ruins_restore.py`（本报告的每条事实都出自它）。

---

## 一、结论（先给）

**❌ 战斗中「直接改盘修废墟」做不到** —— 不是实现难度问题，是**游戏机制**决定的：

| # | 结论 | 依据 |
|---|---|---|
| 1 | **本局的城市复活，改磁盘没用** | 废墟是**开一场新战斗时**注入游戏内存的（`Game.new` → `map_objects.set_destroyed_cities(self.destroyed_cities)`）⇒ 战斗中那座废墟活在**游戏的内存**里，改存档文件碰不到它 |
| 2 | **磁盘上的修改必被游戏覆盖** | ① 战斗存档会把**内存里的** `destroyed_cities` 写回（`Game._save` 的字段表里有它）；② 游戏存档时 `remove_directory('games')` 删掉整个 `games/` 再重写，根 `main.yml` 也从内存重写（`Campaign.save`）；③ 写盘触发点很多：每回合开始、回合结束、离开战斗、退出游戏 |
| 3 | 因此**去掉限制只会得到「假成功」** | 界面提示「已修复」，游戏下一个回合或退出时就把磁盘上的修改覆盖回去 ⇒ 玩家看到的是「改了，但过一会儿又变回废墟」 |

⇒ **但「玩家想让这局的城市复活」这个需求本身是合理的**，只是**修改器无法在游戏运行时
达成**（游戏没给接口）。⇒ 可行的替代方案见第五节。

## 二、取证：四个关键事实（全部来自字节码）

### ① 废墟是「开新战斗」时注入的

`uoc2/state/game/game.pyc` → `Game.new`：

```
LOAD_ATTR  map_objects
LOAD_ATTR  set_destroyed_cities
LOAD_ATTR  destroyed_cities        ← 参数 = 战役级清单
```

⇒ **战斗中的废墟 = 战役清单 `destroyed_cities` 在这场战斗开始时被注入到地图对象里**。
⇒ 推论：**清单是权威**；战斗中的快照只是它的投影。

### ② 战斗存档会把内存里的 `destroyed_cities` 写回

`Game._save` 的名字表：
`dict, _all_game_fields, campaign, prestige, score, in_state, front,
used_card_types_with_unit, destroyed_cities, _save_campaign_game_files, …`

⇒ 战斗存档时，`destroyed_cities` 取**内存里的值**写进存档 ⇒
**我们在磁盘上删掉的那个坐标，游戏会照内存里的旧值写回来**。

### ③ 游戏存档会删掉重写 `games/` 与 `document/`

`uoc2/state/campaign/campaign.pyc` → `Campaign.save`：

```
LOAD_ATTR  remove_directory ; LOAD_CONST 'games'      ← 删掉整个 games/
LOAD_ATTR  _save_campaign_files                        ← 再重写
LOAD_ATTR  remove_directory ; LOAD_CONST 'document'   ← document 也删掉重写
LOAD_ATTR  _save_main_files                           ← 根 main.yml 从内存重写
```

⇒ **废墟的三个写入目标全部落在「游戏会覆盖」的范围里**：
`games/<场景>/cities.yml`、`games/<场景>/forts.yml`（在 `games/` 里）、
根 `main.yml` 的 `destroyed_cities`（从内存重写）。

### ④ 战斗中写盘的触发点很多

| 触发点 | 位置 |
|---|---|
| 每回合开始（存档 archive） | `Game.save_archive_start_turn` |
| 回合结束 / 手动存档 | `GameWorldCtrl._cr_end_turn` / `slot_save` |
| 离开战斗界面 | `GameWorldCtrl.on_leave__active` / `CampaignCtrl.on_leave__active` |
| 退出战斗（挂起/拆世界） | `MainScreenCtrl._cr_world_suspend` / `_cr_teardown_world` |

⇒ **玩家在战斗中改盘，几乎不可能抢在游戏下一次写盘之前** ⇒ 修改必被覆盖。

## 三、风险清单（如果硬要放开限制，会发生什么）

| # | 风险 | 严重度 | 说明 |
|---|---|---|---|
| **R1** | **假成功**：界面说改好了，磁盘上确实改了，但游戏下次写盘就覆盖回去 | 高 | 最可能的结局；玩家会以为功能有 bug，反复重试 |
| **R2** | **本局无效**：即使磁盘改对了，**当前这局**里那座城市仍然是废墟（游戏内存） | 高 | 语义上就没满足需求 |
| **R3** | **游戏自检不一致** | 未知 | U187 的教训：游戏有「状态自检」，发现两个同样主体就崩。废墟状态在**清单 / 场景快照 / 内存地图对象**三处不一致时会不会也触发自检，**离线无法验证** ⇒ 风险不可量化 |
| R4 | 写盘中间态 | 低（与本功能无关） | 我们自己的写盘是原子的（临时文件 → 校验 → 原子替换）⇒ 不会留半写状态；但**游戏**的写盘不是原子的（先删 `games/` 再写）⇒ 写盘中途被打断 ⇒ `games/` 缺失 ⇒ 存档损坏。**这是既有风险**，与本功能无关 |
| R5 | L2 检查点回退 | 中 | 我们**不写** `last_conference/` / `last_game/` ⇒ 游戏里「重置会议 / 重打上一场」可能把这处修改回退 ⇒ 界面要提示用修改器自己的「撤销」 |

⇒ **R3 是关键的不确定性**：任何「游戏运行时改它的存档」的方案都带着这个不可量化的风险。

## 四、为什么现在的限制是对的（但理由要写全）

现���只有半句理由（「游戏会覆盖回去」）。完整的理由是**三条**：

1. **本局改不了**（废墟在游戏内存里）—— 这是**语义**限制，不是技术限制；
2. **磁盘上的改动会被覆盖**（R1）—— 这是**技术**限制；
3. **自检风险不可量化**（R3）—— 这是**风险**限制。

⇒ 所以限制该保留，但**界面提示要写清楚「为什么」和「什么时候能修」**。

## 五、可行的替代方案（三选一，按成本排序）

### 方案 A（最小改动）：把提示写清楚 —— 战斗中点废墟时直接告诉玩家下一步

* 改动量：**只改文案**（战斗中的「修复这一座」按钮禁用 + 说明）。
* 提示内容：「战斗中不能修：游戏会用内存里的状态覆盖存档，而且这一局的城市状态在游戏内存里。
  **退出游戏后**再来修即可（改动会对下一局生效）。」
* 优点：零风险；玩家知道自己该做什么。
* 缺点：玩家仍然要退出游戏。

### 方案 B（推荐的中期方案）：「预约修复」—— 战斗中记下意图，退出游戏后自动应用

流程：

1. 战斗中点废墟 → 修改器**不写存档**，只把「要修哪一座」记进**修改器自己的数据目录**
   （`data/` 下 ⇒ **不受游戏覆盖影响**）；
2. 玩家退出游戏（游戏把内存状态写回存档）；
3. **重新打开修改器** ⇒ 检测到「有待生效的修复」⇒ 读**最新的**存档（游戏写完的版本）
   ⇒ 应用修复（走正常的备份 → 写临时 → 校验 → 原子替换）；
4. 提示玩家「已应用 N 处修复」。

* 改动量：中等（新增一个「待生效清单」文件 + 应用流程 + 「游戏是否还在跑」的判定）。
* 要处理的坑：
  * **必须确认游戏已退出**（否则又是 R1）—— 判定方式：存档 mtime / 锁文件 / 进程名（需实测哪个可靠）；
  * 应用时要用**游戏写完之后的**存档（重新读盘），不能拿旧内容；
  * 待生效清单要能**过期作废**（比如玩家已经手动修过了）。
* 优点：玩家体验接近「立即修复」；不动游戏正在用的存档 ⇒ **不碰 R3**。

### 方案 C：生成「修好的副本」让玩家替换

* 战斗中点废墟 → 修改器把修好的版本**另存为一个新文件**（复用已有的「另存为」能力）；
  玩家退出游戏后，用它替换原档。
* 优点：绝对安全。
* 缺点：多一步手工替换，容易出错（换错文件 / 忘了替换）。

### 方案 D：等游戏提供机制 —— 不可行（游戏包里没有修废墟的功能）

---

## 六、建议

1. **现在**：做方案 A（把提示写清楚）—— 半小时的事，立刻改善体验；
2. **想要「立即修复」**：做方案 B（预约修复）—— 可行且不碰游戏正在用的存档；
3. **不建议**：直接放开「战斗中改盘」（R1 + R2 + R3 三重风险）。

## 七、附：本次顺带确认的 U187 根因（玩家 2026-11-27 提供）

玩家实机结论：**在霸王行动关卡已经开始后给手牌放 82 空降师，而 82 空降师已经部署在场上了**
⇒ 游戏初始检测发现**两个同样主体** ⇒ 自检崩溃。

字节码佐证（`Game.new` 里就有这段自检）：

```
LOAD_ATTR  get_card_type_unit_id      ← 取这张召唤卡对应的 unit_id
LOAD_ATTR  is_unit_id_referenced      ← 这个 unit_id 是不是已被引用
LOAD_CONST 'Card has unit_id set to '
LOAD_CONST ' which is already used in the game!'
```

⇒ **真正的危险不是「手牌有召唤卡」，而是「手牌里那张召唤卡指向的 unit_id 已经被游戏引用」**
⇒ 这正是**货架白名单**已有的那条检查（`used_card_types_with_unit` / `已在手牌`）。

⇒ **未来**若想把 U187 从「手牌侧整类禁掉召唤卡」收窄成「与货架同款的三条检查」，
技术依据已经齐了（玩家 2026-11-27 拍板：**当前设定不变** ⇒ 本轮只记录，不改代码）。
