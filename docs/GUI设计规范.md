## 1. 设计目标与验收判据

三条铁律。每条都必须能**当场检验**，否则不算数。

### 1.1 铁律一：傻瓜式

> 不读任何文档，也能完成"把某个单位的战力调到满并保存"。

| # | 判据 | 怎么验 |
|---|---|---|
| A1 | 核心操作 ≤ **3 步**：选存档 → 悬停滚轮 → 点「应用更改」 | 找个人看着做 |
| A2 | 任何灰掉的控件，**鼠标悬停都能看到原因** | 逐个禁用项试 |
| A3 | 任何写盘前，屏幕上一定先出现「要改什么」的逐条清单 | 点应用，看清单 |
| A4 | 不用记快捷键也能完成全部功能 | 禁用所有快捷键 |
| A5 | 破坏性操作（删除卡牌、下架商品）必须二次确认，且能撤销 | 逐个试 |

### 1.2 铁律二：好看

> 看起来像这款游戏的配套工具，而不是一个查表工具。

| # | 判据 | 怎么验 |
|---|---|---|
| B1 | 单位、特种兵、战区资产**全部用游戏原生贴图**，不自绘替代品 | 逐页看贴图来源 |
| B2 | 配色与静态查看器**同一套 PALETTE**，将来能拼成一个窗口 | 对照 `view_west_campaign.py` |
| B3 | 单位列表里**能看见头像和战力阶梯**，不是一列纯文字 | 看单位页 |
| B4 | 没有默认丑的 ttk 灰控件（Combobox / Scrollbar / Entry 全部改过皮肤） | 走查全页 |

### 1.3 铁律三：丝滑

> 调数值不需要"点进输入框 → 选中 → 输入 → 回车"。

| # | 判据 | 怎么验 |
|---|---|---|
| C1 | 鼠标悬停在**任意可改数值**上，滚轮即改，**无需先选中** | 试所有数值 |
| C2 | 改动 **200 ms 内可见**，不用点"预览" | 眼睛看 |
| C3 | 撤销是一步（按钮或 Ctrl+Z），且**能撤销一批改动**（不只一个） | 改 3 个再撤 |
| C4 | 任何耗时 > 300 ms 的操作有进度反馈 | 打开大存档 |
| C5 | 滚动 60 fps：列表不卡、不跳 | 上下滚 200 个单位 |

## 2. 信息架构

### 2.1 三层

```
┌─ L0 存档选择层 ──────────────────────────────────────────┐
│  启动即这一屏。列出所有存档，按最近修改倒序。             │
│  点一个 ⇒ 进 L1。                                        │
└──────────────────────────────────────────────────────────┘
                          ↓
┌─ L1 功能层（主窗口）──────────────────────────────────────┐
│  左侧 Rail：7 个功能页。右上：撤销 / 应用更改。           │
│  每个功能页里再分出 L2 对象层。                          │
└──────────────────────────────────────────────────────────┘
                          ↓
┌─ L2 对象层 ──────────────────────────────────────────────┐
│  单位详情 / 特种兵图鉴 / 商店条目 / 总部条目 / 卡牌条目   │
└──────────────────────────────────────────────────────────┘
```

### 2.2 为什么用左侧 Rail 而不是顶部标签页

**【决策】** 7 个功能页用**左侧竖排 Rail**（图标 + 中文名），不用 Notebook 标签。

理由：

1. 中文标签"战区资产""特种兵与兵库"太宽，7 个标签塞不下 1440 px；
2. Rail 每项有 **48 px 宽的状态位**，能显示"待应用 3 处"这类角标 —— 标签页放不下；
3. Rail 项可以**直接显示禁用原因**（灰 + 右侧小字"战斗中才可用"）；
4. Rail 可以**折叠成 56 px 图标条**，给单位列表让出空间；
5. 将来与静态查看器合并时，Rail 是可以左右拼接的（左看战役数据、右改存档）。

### 2.3 功能页清单

| # | 页 | 内容 | 能力位 | 备注 |
|---|---|---|---|---|
| 1 | 概览 | 存档体检、声望/分数、备份与撤销栈 | 恒可用 | |
| 2 | 单位 | 名册、战力、XP、**特种兵挂载**、改名 | `can_edit_units` | **主战场**；特种兵挂载**并入本页** |
| 3 | 总部 | 总部条目、兵库存量、CP | `can_edit_hqs` | |
| 4 | 卡牌 | **手牌**（`cards.yml`）+ **货架**（`main.yml.card_store`）+ 图鉴 | `can_edit_hand` / `can_edit_shelf` | 货架只在会议阶段存在 |
| 5 | 商店 | 按战线分组的商品、价格、数量 | `can_edit_store` | |
| 6 | 战区资产 | 11 类资产的可用次数 | `can_edit_theater_assets` | 只在战斗中 |

> **【2026-11-18 用户拍板 · U9】原第 3 行「特种兵」整页取消** ——
> 挂载 / 卸下是「某个单位的事」，跟单位放在一起才对 ⇒ Rail 从 7 页变 **6 页**。
> 原页面的「375 种图鉴（只读）」价值**没丢**：变成单位页备选池上的
> 「显示全部 375 种」开关（§7.3.4）。

## 4. 视觉规范

### 4.1 调色板

**【决策】** 前 10 色**沿用静态查看器**的 `PALETTE`（`tools/view_west_campaign.py:22`），保证两个程序将来拼一起不打架；
后 6 色是本次新增，专供"可改 / 不可改 / 已改"的状态表达。

| token | 值 | 用途 |
|---|---|---|
| `window` | `#f4f6f8` | 窗口底 |
| `surface` | `#ffffff` | 卡片 / 面板底 |
| `surface_alt` | `#eef2f6` | 工具条 / 次级面 / 表头 |
| `border` | `#d4dbe3` | 分隔线 / 描边 |
| `text` | `#1f2933` | 正文 |
| `muted` | `#5c6b78` | 次要文字、禁用说明 |
| `accent` | `#245b8f` | 主色：选中、主按钮 |
| `accent_dark` | `#17456f` | 深主色：表头、标题 |
| `accent_light` | `#dceaf7` | 浅主色：提示条 |
| `selection` | `#cfe3f5` | 选中行底色 |
| **NEW** `ok` | `#1e6b3a` | 已满 / 成功 / 已应用 |
| **NEW** `ok_light` | `#e4f2ea` | 同上的浅底 |
| **NEW** `warn` | `#8a5a00` | 软警告 |
| **NEW** `warn_light` | `#fdf3e0` | 软警告浅底 |
| **NEW** `danger` | `#a4262c` | 破坏性操作（删除 / 下架 / 撤销） |
| **NEW** `danger_light` | `#fbe9ea` | 破坏性操作浅底 |
| **NEW** `stage` | `#e4eaf1` | **贴图衬底**（单位头像 / 特种兵兵牌） |
| **NEW** `stage_sup` | `#b9c6d6` | **被压制兵力**（血条上的淡色段） |

**贴图衬底为什么是浅色而不是深色**：
游戏贴图（单位立绘、特种兵兵牌）**多数本身没有底色**，是带 alpha 的透明 PNG。
深色衬底虽然能衬出轮廓，但**和整个浅色调界面割裂**，看久了发闷（实测深底观感确实"脏"）。
⇒ 统一用**温和的蓝灰** `#e4eaf1`（与 `accent` 蓝同色系、比 `surface_alt` 略深），
再配 1px `border` 描边 —— 贴图轮廓看得清，又不跳脱。
深色只保留给**真正的浮层**（tooltip、对话框、下拉菜单），不用于大面积贴图区。

### 4.1b 血量段格条的两层配色

| 段 | 颜色 | 含义 |
|---|---|---|
| 实心 | `accent` | **未被压制的兵力**（`act_st`） |
| 实心但淡 | `stage_sup` | **被压制的兵力**（`sup_st`）—— 还在，但不能行动 |
| 空心 | `surface_alt` + `border` | 离满血量还差的几格 |

⇒ 一眼能看出"我有多少人、其中多少被压住了"。


### 4.2 字体

| 角色 | 字体 | 字号 | 说明 |
|---|---|---|---|
| 页面标题 | Segoe UI Bold | 16 | |
| 区块标题 | Segoe UI Bold | 11 | |
| 正文 | Segoe UI | 10 | |
| 次要 | Segoe UI | 9 | 禁用原因、提示 |
| **数值** | **Consolas** | 10–14 | **等宽**：滚轮变值时数字不左右跳 |

**【决策】** 所有"会被滚轮改的数值"一律用 Consolas 等宽。
普通比例字体在 `5 → 6 → 7` 之间宽度变化，滚动时整列会左右抖动 —— 这是"丝滑"最容易翻车的地方。

### 4.3 间距刻度

`4 · 8 · 12 · 16 · 24 · 32`（px）。任何内边距只能用这几个值。

### 4.4 控件皮肤

ttk 的默认控件（尤其 Combobox、Scrollbar、Entry）很丑，必须改：

| 控件 | 规格 |
|---|---|
| 表格（Treeview） | 行高 30，斑马纹 `#ffffff`/`#fafbfc`，选中 `selection`，悬停 `accent_light` |
| 表头 | `accent_dark` 底 + 白字 + `table_heading` 字体 |
| 滚动条 | `clam` 皮肤重绘：滑块 10 px 圆角、`borderwidth=0`、槽 `window` 色 |
| 输入框 | 白底 + 1px `border` + 聚焦时边框转 `accent` |
| 下拉框 | 同输入框；箭头区单独着色 |
| 主按钮 | `accent` 底白字；禁用时 `surface_alt` 底 `muted` 字 |
| 危险按钮 | `danger` 底白字（删除 / 下架） |
| 工具条 | `surface_alt` 底 + 上下 1px `border` |

### 4.5 圆角与阴影

Tk 没有真圆角。用**两层叠加**模拟：底层 `surface` 画 1px `border` 边框，顶层贴一张带 alpha 的圆角 PNG（运行时用 §10.2 的 PNG 管线生成，一次性烘成 9-patch 风格的小图，缓存复用）。
**不做**每控件独立阴影 —— 阴影只用在浮层（tooltip / 对话框 / 下拉菜单）。

### 5.2 特种兵 7 张图各是什么

**【实证】** 尺寸由 PNG IHDR 直读，**不要照文件名猜**（我第一次就猜错了）：

| 文件 | 实测尺寸 | 真实用途 | GUI 用在哪 |
|---|---|---|---|
| `sheet_act.png` | 24×30 | 战斗条上的**活跃兵**小图标 | 列表行内的小徽标 |
| `sheet_sup.png` | 24×30 | 战斗条上的**压制兵**小图标 | 列表行内的小徽标 |
| `status_act.png` | 39×50 | 状态面板的活跃兵 | 详情页小图 |
| `status_sup.png` | 39×50 | 状态面板的压制兵 | 详情页小图 |
| `sheet_large.png` | 52×68 | 战斗条上的大号单位图 | 详情页主图 |
| **`hq_action_icon.png`** | **160×160** | 总部行动图标 | **特种兵图标（选它）** |
| `hq_menu_icon.png` | 72×48 | 总部菜单图标 | 菜单项 |

**【决策】** 特种兵图标用 `hq_action_icon.png`（160×160，唯一够大的）——
用在**单位页的已挂槽位 + 备选池**（§7.3.4），缩到 64×64 画。

### 5.3 单位头像：`sheet_L` 还是 `sheet_R`

**【实证】** 字节码 `uoc2/common/sheets/combat_sheet.pyc::_render_combat_sheet`：

```
进攻方：'unit/' + combat.att.type + '/sheet_L'
防守方：'unit/' + combat.dfe.type + '/sheet_R'
```

`uoc2/common/sheets/unit_sheet.pyc::_render_unit_sheet`（单位详情面板）**永远用 `sheet_L`**。

⇒ **【决策 · 2026-11-18 用户拍板】** GUI 的头像查找规则：

```
1. 在 unit/<type>/ 里找 sheet_L.png   ← 优先（大小写不敏感）
2. 找不到 → 找 sheet_R.png            ← 回退
3. 都没有 → 占位方块（不崩）
```

* 列表 / 详情 / 图鉴**一律走这条规则**，不需要调用方判断"该用哪张"；
* **大小写不敏感是必须的** —— 实测 `unit/ger_pz_dlc7/` 里是 **`sheet_l.png`（小写 L）**，
  其余 628 个是 `sheet_L.png`；大小写敏感会把虎式（Pz）类型的头像弄丢；
* 629 个类型**全部有 `sheet_R`**，所以第 2 步几乎不会触发，但留着更稳（mod 新增类型可能只有 R）。


### 5.4 战力阶梯（step）语义

> **⚠ 2026-11-18 用户拍板（U9）：单位页不再显示战力阶梯块** ——
> 那个 `step` 图只是把 `equipment_q` 换个说法画一遍，兵力条 + 数字已经说清了
> （用户原话：「战力阶梯这个块没有任何用处，直接删掉」）。
> ⇒ 本节的语义知识**保留存档**（万一以后要查），但 **UI 上不画**。

**【实证】** `uoc2/game_world/hq_ctrl.pyc::HQCtrl._fp_helper`：

```python
step_img = 'steps/step{}'.format('_' + equipment + '_' + equipment_q if equipment else '')
text    = locale.get(text_id).format(locale.get(name_brief), n)
#  text_id: equipment 为 None → id_n_steps_infantry
#          equipment_q == 1     → id_n_steps_mechanized
#          否则                  → id_n_steps_armor
```

中文模板：`id_n_steps_infantry = "{}步兵战力（{}）"` ⇒ 第二个 `{}` 就是**步数 n**。

## 6. 交互规范

**这是全文最重要的章节。** 用户的原始诉求"鼠标悬停在单位上，滚轮就能调节血量"就落在这里。

### 6.1 滚轮调值 —— 统一规则

所有**可改数值**用同一套行为，玩家只需要学一次。

| 修饰键 | 行为 | 适用 |
|---|---|---|
| 无 | **± 1** | 所有数值 |
| `Ctrl` | **± 10** | 大数（XP、声望、分数、价格、商店数量） |
| `Shift` | 直接到**边界**（最小 0 / 最大值） | 所有数值 |
| `Alt` | ± 1 但**跳过一个刻度**（用于 0.5 这类小数） | 预留 |

**完整反馈链**（一次滚轮 = 这一整套，缺一环就不算"丝滑"）：

1. **悬停高亮**（120 ms）：目标控件边框转 `accent`，底色转 `accent_light`；
2. **数值即时变**：不写盘，只改内存里的 pending 值；
3. **数值脉冲**（150 ms）：变化的数字短暂染 `accent` 色再淡回 —— 让眼睛抓住"哪里动了"；
4. **血条同步**：段格条、阶梯图标跟着变（见 §6.1b 的两层规则）；
5. **待应用计数 +1**：Header 的「应用更改」按钮上出现角标；
6. **不弹任何对话框**。

**边界处理**：

* 到达上限再往上滚：**数字闪一次 `warn` 色**，值不变（不静默、不循环、不跳变）；
* 往回滚回到原值：**该条待应用记录自动消失**（避免"改了又改回来"却还留在清单里）；
* 数值超出核心库允许范围（硬拦类，如 `xp > 400`）：**允许你先滚过去**，但在应用时会被 `plan.errors` 拦下并在清单上标红说明 —— 不在滚动时打断你。

**【决策】** 滚轮**绝不直接写盘**。所有改动先进"待应用"清单，一键提交。
理由：写盘要备份 + 校验 + 原子替换，滚轮一格就写一次会把磁盘写爆，也没法"撤销一批"。

### 6.1b 血量的两层逻辑 ⭐

**【实证】** 存档里单位的兵力是**两个字段**：

```
当前血量 tot_st = 未被压制 act_st + 被压制 sup_st
血量上限        = 类型定义的 max_st（不在存档里，§5.3）
```

核心库可改字段：`Edit.unit_field(unit_id, "act_st", v)` / `("sup_st", v)`
（合计超过 `max_st` 是**软警告**，不硬拦 —— `handlers.py:145`）。

⇒ **【决策 · 2026-11-18 用户拍板】** 血量做成**两套滚轮区**，各管一个字段：

```
┌──────────────────────────────────────────────────┐
│  血量条（段格）                    数字区        │
│  ▓▓▓▒▒░░            ← 滚轮调「被压制的量」  5 / 7 │
│  实=未被压制 淡=被压制 空=还差                      │
└──────────────────────────────────────────────────┘
      ↑ 滚轮调 sup_st                      ↑ 滚轮调 tot_st（当前血量）
```

| 滚轮位置 | 调的量 | 另一个字段怎么变 |
|---|---|---|
| **数字区**（血量条右侧的数值） | **当前血量 `tot_st`** | `sup_st` 保持不变 ⇒ `act_st = tot_st − sup_st` 变 |
| **血条本体**（段格条） | **被压制的量 `sup_st`** | `act_st` 保持不变 ⇒ `tot_st = act_st + sup_st` 跟着变 |

两个量**互相独立**可调（自由度 = 2），`act_st` 是派生量。

**约束与夹取**：

| 情况 | 处理 |
|---|---|
| 调 `tot_st` 时 `tot_st < sup_st` | `act_st` 会变负 ⇒ **夹到 0**，此时 `tot_st` 实际取 `sup_st` |
| 调 `tot_st` 时 `act_st` 超上限 | 夹到 `max_st − sup_st` |
| 调 `sup_st` 时 `sup_st > tot_st` | 夹到 `tot_st`（`act_st` 保持 0） |
| 目标类型未知（`max_st` 拿不到） | **不夹取**，只夹 `≥ 0`；上限显示 `?` |

**写盘时生成两条 Edit**（一次滚轮可能同时动两个字段）：

```python
Edit.unit_field(uid, "act_st", new_act)
Edit.unit_field(uid, "sup_st", new_sup)
```

⇒ 「待应用」清单里**一条记录显示两个字段**，例如：

```
第 1 装甲师 · 兵力
   当前血量 5 → 7        被压制 1 → 1
```

**为什么要两层而不是一根条**：玩家想改的其实是两个不同的事 ——
"我的人太少了"（改总量）和"我的人被压住了"（改压制量）。
一根条只能表达一个，另一个就得进编辑框手输 —— 那就不是"傻瓜式"了。

⚠️ **软警告必须说清楚**：战斗外改 `act_st` / `sup_st` 会被游戏在下次开打时**重算覆盖**
（规范 §3.5.8 存活性矩阵）。⇒ 悬停这两个滚轮区时，tooltip 里固定带一句
"战斗外改会在下次开打时被重算；战斗中改立即生效"。

### 6.2 悬停（hover）

| 目标 | 悬停表现 |
|---|---|
| 单位列表行 | 行底色转 `accent_light`；右侧滑出**快速条**（战力 −/+、XP −/+） |
| 单位头像 | 浮出**大图 tooltip**（原图等比缩到 240 px 宽） |

1.5 s 无移动后消失、右上角小箭头指向目标。

### 6.4 确认流程（三道关）

```
   玩家改动
      │
      ▼
┌─────────────────┐
│ ① 待应用面板     │  底部常驻面板，实时列出：对象 · 字段 · 旧值 → 新值
│   （随时可看）   │  软警告用黄色条插在对应行上方
└────────┬────────┘
         │ 点「应用更改」
         ▼
┌─────────────────┐
│ ② 确认对话框     │  列出将要被改动的**文件**（units.yml / store.yml …）
│                 │  列出改动条数、备份文件名
│                 │  [取消]              [应用更改]
└────────┬────────┘
         │ 核心库执行
         ▼
┌─────────────────┐
│ ③ 结果 Toast     │  ✓ 已保存 · 备份 xxx_BACKUP.usg   [撤销]
│                 │  ✗ 失败 · 原因一句话（原存档未改动）
└─────────────────┘
```

**【决策】** ②的对话框**必须列出文件名**，因为玩家要知道自己的存档里哪些文件被动了。

**软警告 vs 硬拦在 GUI 上的区别**：

| 核心库 | GUI 表现 |
|---|---|
| `plan.errors` | 确认框的「应用更改」按钮**禁用**，错误以红条列出，鼠标悬停给详细原因 |
| `plan.warnings` | 确认框顶部一条黄条"有 2 条软警告"，**仍可应用**，点开看详情 |

### 6.5 撤销

* 顶栏「↶ 撤销」按钮 + `Ctrl+Z`；
* 按钮上直接显示**人话摘要**：`撤销：单位 3 战力 5 → 7`（来自 `save.undo_peek()`）；
* 栈空时按钮禁用，悬停显示"没有可撤销的操作"；
* 撤销本身也走备份 + 校验管线（核心库已实现），失败要明确说"撤销栈基准已过期，拒绝执行"；

### 6.7 禁用与原因

所有禁用态统一处理：

**段格条（兵力条）**：这是"血量条"，做成**离散格**而不是连续条 —— 因为血量的最小单位就是 1 点，

**一层格子同时表达两件事**：实心段 = 未被压制的兵，淡色段 = 被压制的兵（§6.1b）。

#### 7.3.1 数值在游戏包里，存档里只有引用

> **【实证 · 2026-11-18 · `e156`】** 特种兵的**数值在游戏包里，不在存档里**。
> `entity_types/specialists/*.yml`（**375 个类型**，已实测目录文件数）定义
> `attack / defense / armor / artillery / att_idx / dfe_idx / flags / nationality / faction`；
> 存档 `units.yml` 里的 `specs` **只有** `{active, captured, idx, type}`
> —— 类型引用 + 状态标志，**一个数值都没有**。
>
> ⇒ **改数值 = 改游戏包**（mod 范畴，超出 L1 白名单）⇒ **本修改器不做**；
> ⇒ 但「**哪个单位挂了哪些特种兵**」在存档里 ⇒ **可以加、可以卸**。

> **⚠ 375 种里有「坦克」** —— `us_armx_42`（M4谢尔曼）等**装甲单位也在 specialists 表里**
> （实测：只存在于 `entity_types/specialists/`，`unit_types/` 里没有）。
> 这不是数据错乱，是游戏自己的设计 ⇒ **备选池照实显示**，不做人工剔除。

#### 7.3.2 挂载规则（`e162` 字节码坐实 · G3 必须照此实现）

游戏自己的判定在 `uoc2/state/entities/unit.pyc::UnitState`：

```python
# get_available_spec_types —— 游戏列「可挂清单」的方式
return [sp for sp in specialist_types.get_all_types()      # 全部 375 种
        if self._can_add_specialist_no_len(sp)]

# _can_add_specialist_no_len —— 单个能不能挂
if not specialist: return False
if not captured:
    if self._type.faction != specialist.faction: return False
    if self._type.nationality != specialist.nationality:
        nat = nationality_types.get_type(self._type.nationality)
        if nat.parent_nationality != specialist.nationality: return False
return True

# can_add_specialist —— 还要看槽位够不够
if len(self.specs) >= self._type.max_spec: return False
```

⇒ **三句话版**（玩家能听懂的那版）：

| 条件 | 规则 | 中文说法 |
|---|---|---|
| 阵营 | `unit.faction == spec.faction` | **阵营必须相同** |
| 国籍 | `unit.nationality == spec.nationality` **或** 单位国籍的 `parent_nationality == spec.nationality` | **国籍必须相同**，或单位国籍的「父国籍」与特种兵国籍相同 |
| 容量 | `len(specs) < max_spec`，`max_spec = min(3, 类型表 max_spec)` | **最多 3 个**，实际按单位类型 |

* 实测过滤后的可挂种数：`us_arm_42`（同盟/美）**23** 种 / `sov_inf_41`（苏联）61 种 / `ger_inf_40`（轴心/德）97 种；
* `captured=True` 的单位**跳过阵营 / 国籍检查**（游戏逻辑，UI 照抄即可）；
* **没有 flags 过滤** —— `get_available_spec_types` 就是「全部 375 种过一遍规则」
  ⇒ 备选池**不做**额外的「按特殊类型筛选」。

#### 7.3.5 备选池的口径：默认只列「本战役有的」（U10）

> **【2026-11-18 用户拍板】** 备选池**默认只显示本战役的特种兵**。
> 理由三条：防止游戏出怪 bug、375 种太多玩家改不动、
> 1939 年的战役挂 1945 年的特种兵很出戏；
> 另外留一个「**显示全部**」的开关。

**口径**

```
战役默认池(campaign) = { 该战役 所有战线 × 所有会议 的商店 `spec:` 条目 }
                     ∪ { 该战役 所有场景 units.yml 里 `specs[].type` 出现过的 }
最终候选             = 战役默认池 ∩ e162 规则可挂集合（阵营 + 国籍/父国籍）
```

**为什么是「商店 ∪ 场景」而不是只用商店**（`e163` 实测）

| 口径 | 玩家阵营下漏掉「游戏自己用过」的特种兵 | 结论 |
|---|---|---|
| 只用商店 | **113 种**（`us_spec_42` / `ff_recon_42` / `ger_at_40` …） | ❌ 会把游戏自己在用的藏起来 |
| **商店 ∪ 场景** | **0 种** | ✅ **零假阴性** |

**实测数据**（15 个战役全跑）

| 战役 | 玩家阵营 | 商店池 | 战役默认池 | e162 规则内均 | **∩战役默认池均** |
|---|---|---|---|---|---|
| `base/west` | allies | 18 | 45 | 30.0 | **9.0** |
| `dlc1/blitzkrieg` | axis | 7 | 37 | 98.4 | **8.2** |
| `dlc4/stalingrad` | axis | 15 | 54 | 98.4 | **18.7** |

`ger_inf_40` @ `dlc4/stalingrad` **97 → 18**；
`sov_inf_41` @ `dlc9/berlin` **61 → 19**。

**战役默认池的三个性质**（都是优点）

1. **只卖玩家一方阵营** —— allies 战役只有 allies，axis 战役只有 axis，soviet 战役只有 soviet
   ⇒ 天然就是「我方」，**不用再按存档的 `player_faction` 过滤**；
2. **年代自洽** —— blitzkrieg 只有 `_39/_40/_42`、barbarossa 只有 `_40/_41/_42`、desert 只有 `_42`
   ⇒ 1943 年的战役不会出现 1945 年的特种兵；
3. **数量收敛** —— 每战役 6–41 种（对 375 种）。

> 18~41 个条目根本没有年份 ⇒ **只能靠商店 / 场景集合**。

**三层兜底**（用户拍板）

| 正常 | 战役默认池 ∩ 规则 | 池标题写明「XX 战役默认」+ 种数 |

  避免一屏塞满（傻瓜式原则：常用的滚轮可调，冷门的不抢眼）。

### 7.5 卡牌页

> **【实证 · 2026-11-18 · `e157` / `e158` / `e160`】修正前一版**：卡牌商店**确实存在**。
> 上一版"游戏里没有卡牌商店"是**取样错误** —— 当时那份存档不在会议阶段，
> `main.yml.card_store` 自然是 `None`。用**会议阶段已激活卡牌商店**的存档复核后，机制如下。

**两个容器，一套字段**

| 容器 | 位置 | 含义 | `is_free` |
|---|---|---|---|
| **卡牌商店货架** | `main.yml` → `card_store` | **在售**的牌（会议阶段才有） | `False` = 要花**声望**买；`True` = 免费 |
| **手牌** | `cards.yml` | 你**已经拿到**的牌 | 均为 `True` |

条目字段（两者完全一致）：`{card_type, is_free, position, unit_id, used}`。

**货架是怎么来的（字节码实证）**

```
进入会议 set_conference()
  └─ create_random_card_data(card_store_limit[level], all_free=False)
       ├─ 权重 = 全局 card_meta_types_base_probabilities（15 / 6 / 3 三档）
       │         → common_conferences 的会议文件覆盖
       │         → 各前线 card_probability_scales 再缩放
       ├─ 按权重抽 card_store_limit[level] 张
       └─ 前 card_store_free_cards[level] 张标成 is_free=True（免费送）
```

| 常量（`constants.pyc`，按难度 easy/normal/classic/hard） | 值 |
|---|---|
| `card_store_limit`（货架格数） | 5 / 5 / 5 / 5 |
| `card_store_free_cards`（免费几张） | 2 / 1 / 0 / 0 |
| `card_deck_limit`（手牌上限） | 5 / 5 / 4 / 3 |

**购买做了什么（`conference_actions.pyc::BuyCard`）**

1. 前置：商店存在 → 该 `position` 有货 → 手牌未满 → 目标手牌位未被占；
2. 价格：`0`（`is_free`）否则 `card_types.get_type(card_type).cost`
   —— **扣的是声望 `prestige`**，不是 CP；
3. 结果：`card_store.pop(position)` + 牌进手牌；
4. 撤销：`conference_start_state` 快照（`store_cards` / `restore`）—— 会议内操作可回滚。

**能不能改？—— 能。** `Campaign.load` 直接从存档读 `card_store`，**加载时不重掷**；
重掷只发生在 `set_conference`（进入**新**会议时）。
⇒ **货架可以改**：换牌 / 改成免费 / 下架 / 上架（`position` ≤ 货架格数）。
⇒ **但下次进入新会议会被重掷覆盖** —— 界面必须写明这一点。

#### 7.5.1 ★ 可上架白名单：只允许改成「商店本来就能生成」的卡

**【决策 · 2026-11-18 用户提出】** 用户担心：
> 有些登陆和空降卡牌会召唤相关单位，如果这个战役本来没有设定这个单位，
> 大概率游戏要崩溃。既然你能知道卡牌商店的生成抽选规则，
> 我们改卡牌的时候也仅允许改成商店能自然生成的卡牌，其他卡牌屏蔽掉。

**这个担心成立，机制如下（`e160` 实证）**：

| 环节 | 事实 | 依据 |
|---|---|---|
| 战役名册 | `document/units.yml` = 战役**全部**单位（实测 blitzkrieg 835 个） | `CampaignDoc._load` |
| 卡→单位登记表 | `document/main.yml.card_type_units` = 哪些卡召唤名册里**哪个 id** | `CampaignDoc.get_card_type_unit_id` |
| 已召唤记录 | 根 `main.yml.used_card_types_with_unit` | `Campaign.get_cards_probabilities` |
| 实测 | blitzkrieg：`{tactical_para_german: unit_id 718}`；718 = 名册里的 `ger_fsjg_40`（德国伞兵团） | `e160` |

**崩溃是怎么发生的**（`BuyCard.do`）：

```python
c = campaign.card_store.pop(position)
self._create_campaign_unit = bool(c.unit_id) and (c.unit_id not in campaign.units)
campaign.add_card(card_type=c.card_type, unit_id=c.unit_id, is_free=c.is_free, ...)
```

* `unit_id` 为 **None** ⇒ **不会召唤单位**，但卡进了手牌 ⇒
  玩家用这张卡时游戏找不到对应单位 ⇒ **崩**；
* `unit_id` 指向名册里**别的**单位 ⇒ 召唤出**错误的单位**。

⇒ 所以**不能只靠"卡牌类型存在于游戏包"来放行**。

**规则（逐条复刻 `Campaign.get_cards_probabilities`，`e160` 已用两个存档验证）**：

```
可上架卡牌 = { ct :  ∃ meta_type, p(meta_type) > 0,
                  ct.faction == player_faction,            ← 存档 document/main.yml
                  ct.meta_type == meta_type,
                  (¬ct.has_unit)                            ← 不召唤单位 ⇒ 无条件可上架
                  OR ( ct ∈ card_type_units                ← 本战役登记过 ⇒ 有单位可召唤
                       ∧ ct ∉ used_card_types_with_unit    ← 还没召唤过
                       ∧ ct ∉ 当前手牌
                       ∧ (units.get(unit_id) 不存在 OR 该单位未阵亡) ) }
```

**实测两个存档（`e160`，脚本在 `docs/证据脚本/e160_card_whitelist.py`）**：

| 存档 | 玩家阵营 | 可上架 | 被屏蔽的原因（举例） |
|---|---|---|---|
| blitzkrieg / c_40_06 | axis | **13 / 39** | 26 张全是「阵营 allies/soviet ≠ 玩家 axis」 |
| stalingrad / c_42_07 | axis | **11 / 39** | `naval_bombardment_axis`：本次会议概率 = 0（会议覆盖成 0.0）；`tactical_para_german`：**本战役没有可召唤的单位** |

**两个存档的真实货架，每一张都落在算出来的候选集内**（`⇒ 真实货架每张都在候选集内: True`）
—— 这条是规则正确性的判据。候选集里没被抽到的那几张，是 `random.choices` 的随机结果。

**界面怎么表现**（【决策】）：

* **换牌对话框 / 上架对话框只列可上架的那几张** —— 不列被屏蔽的，
  避免玩家以为"游戏能抽到但不让改"；
* **图鉴 39 种照旧全列**（图鉴是手册），但被屏蔽的**置灰**，
  鼠标悬停给原因（例："本战役没有可召唤的单位"、"阵营 allies ≠ 玩家 axis"）；
* **核心库必须自己再校验一遍** —— 不能只靠 GUI 挡，
  `Edit.card_store_set` / `card_store_add` 要在写盘前拒绝不在白名单里的卡牌。

**⚠️ 白名单是"当前存档 + 当前会议"的状态**：
换战役、换会议、玩到下一场会议，白名单都会变
（阵营不变，但会议概率覆盖会变，单位也会被召唤掉）。
⇒ **每次开卡牌页都重算**，不要缓存成静态表。

#### 7.5.2 `is_free` 开关（手牌 + 货架都有）

**【决策 · 2026-11-18 用户提出】** 不管卡在手牌还是货架，都给一个按钮切换 `is_free`。

两处**语义不同**，界面上要区分：

| 位置 | `is_free` 的作用 | 改了会怎样 |
|---|---|---|
| **货架** | **购买价**：`True` ⇒ 价格 0（不扣声望）；`False` ⇒ 价格 = 卡的 `cost` | 真实影响 —— 把付费卡改免费 = 白嫖 |
| **手牌** | **没有玩法影响** —— 只改 tooltip 文案（`id_tooltip_deck_card_free` / `_paid`）和卡背贴图（`face_down_free` / `face_down`） | 只是"来源标记"，改坏也无所谓 |

⇒ **货架上的开关要标清当前状态**（"改成免费" / "改成收费"），
并提示"免费卡不扣声望"；
**手牌上的开关要说明它只影响显示**（tooltip 与卡背），免得玩家以为能刷声望。

* 手牌改 `is_free` = `Edit.card_set(position, "is_free", value)`（**核心库目前没有，要补**）；
* 货架改 `is_free` = `Edit.card_store_set(position, is_free=...)`；
* 游戏里免费卡数由难度决定（`card_store_free_cards`），
  **手动改的要标注"手动改的"**，不能让玩家以为是游戏发的。

### 7.6 商店页

> **【实证 · 2026-11-18 · `e154`】** 结构要先说清，否则界面会做错：
>
> * 存档 `store.yml` = **`{战线: {store: [...], elite_store: [...]}}`** ——
>   是**两层**：普通商店 + **精英商店**（游戏字节码里有
>   `copy_to_elite_store` / `remove_elite_store`）；
> * 条目字段：`{spec XOR equipment, nationality, price, quantity}`；
> * **价格与数量都在存档里**，不是从 Conference 文件现算的 ——
>   字节码 `campaign.pyc::_load_campaign_game_files` 读存档后调
>   `conference.set_store_data(...)`，**用存档覆盖会议默认**；
>   写回时 `get_store_data()` 也只认内存里那份。
>   ⇒ **游戏不会拿包默认盖回去，改了就是改了**；
> * 实测对比（front=south, conference=c_42_07）：包默认 19 条 / 存档 13 条
>   —— 少的 6 条是游戏自动下架的；3 条 `quantity` 递减（20→19 / 10→6 / 3→1）；
>   **`price` 零差异**；
> * schema（`data_validation/force_pool.pyc::_force_pool_record` + `store_schema`）：
>   `price` **必填**且非负整数、`quantity` **必填**且为正整数、
>   `spec` 与 `equipment` **Exclusive（二选一，不能都给）**、
>   三个取值都要落在游戏定义的集合里。

**这一页能做什么（结论）**

| 操作 | 能？ | 依据 |
|---|---|---|
| 改**价格** | ✅ 任意非负整数 | `price` 在存档里，schema 只要求非负 |
| 改**库存** | ✅ 任意正整数 | `quantity` 在存档里，schema 只要求正整数 |
| **上架新商品** | ✅ 但**商品本身**必须是游戏定义过的 | `spec` / `equipment` / `nationality` 都要过枚举校验 |
| 下架 | ✅ 删条目（不是设 0） | `quantity: 0` 会被 schema 拒绝 |
| 加**全新种类**（游戏里没有的特种兵） | ❌ | schema 枚举校验会失败 |

* 按 `front` 分组（`catalog.fronts(campaign_id)` 给出战线列表）；
* 普通店 / 精英店做成两个 tab（精英店为空时显示说明卡，别画空表格）；
* 价格 / 库存**滚轮可调**（库存下限 1，上限给个宽松的值）；
* 「下架」是破坏性操作 ⇒ 危险色 + 二次确认；
* **上架对话框里的候选**来自游戏包：特种兵类型（375）× 国籍（34 种实测）、
  兵种（`infantry` / `armor`）× 国籍 —— 都在 `catalog` 里查，**不写死**；
* 上架 = `Edit.store_add(front, sub, entry)`（**核心库已实现**，见 §8.1）——
  ⚠️ `sub` 是**子商店**（`store` 普通 / `elite_store` 精英），
  `store.yml` 是两层结构；本会议没启用精英商店时（`elite_store: null`）
  只能上架到普通商店，核心库会**硬拦**并说明原因；
* **改价 / 改量 / 下架**同理要带 `sub`：
  `Edit.store_set(front, sub, index, field, value)` / `Edit.store_remove(front, sub, index)`。

#### 8.1.3 两处判定逻辑的纠正

**① `card_add` 的 `unit_id` 校验语义原来是错的**

原来是这样：

```python
if info.get("has_unit") and unit_id is None:
    报错 "带单位，必须指定 unit_id"
if unit_id is not None and unit_id not in w.save.roster_ids():
    报错 "unit_id 不在战役名册里"
```

**问题**：`unit_id` 的真实语义不是"名册里任意一个单位"，而是
**`document/main.yml.card_type_units` 里为这张卡登记的那个预留 id**。
实测 blitzkrieg 的 `tactical_para_german` → `unit_id = 718`（名册里的 `ger_fsjg_40` 德国伞兵团），
而 718 **此刻还不在存档的 `units.yml` 里**（还没被召唤过）——
所以"在名册里"这条只是碰巧成立，语义是错的。

**已改成**：

```python
if info.get("has_unit"):
    预留 id = document/main.yml.card_type_units[card_type].unit_id
    → 取不到 ⇒ 报错「本战役没有这张卡可召唤的单位」
    → 传进来的 unit_id 必须与它一致 ⇒ 否则报错
    → 都没传 ⇒ 自动补上预留 id
else:
    unit_id 必须是 None
```

理由见 §7.5.1：`unit_id` 给错 ⇒ 召唤出**错误的单位**；
给 None ⇒ 牌进手牌但没有单位 ⇒ 用卡时崩。

**② `store_set` / `store_remove` 的 `index` 语义原来错了**

真实结构是 `{战线: {store: [...], elite_store: [...]}}`（两层），
⇒ `index` 必须**带子商店**。

```python
# 原来（错）
Edit.store_set(front, index, field, value)
Edit.store_remove(front, index)

# 现在（对）
Edit.store_set(front, sub, index, field, value)   # sub: "store" | "elite_store"
Edit.store_remove(front, sub, index)
Edit.store_add(front, sub, entry)                 # 新增：上架
```

⚠️ 这是**破坏性 API 变更**（核心库还是 0.1.0，GUI 尚未开工 ⇒ 改在前面最划算）。
`sub` 传错值会**硬拦**；`elite_store` 是 `null`（本会议没启用）时也会**硬拦**并说明原因。

#### 8.1.4 ⚠️ 本轮还揪出的两个真 bug（核心库原先的）

| bug | 现象 | 根因 | 已改成 |
|---|---|---|---|
| **手牌与货架命名反了** | `view.hand` 装的是**货架**，`view.cards` 装的是**手牌** | `container.py` 把 `cards.yml`（手牌）和 `main.yml.card_store`（货架）搞混 | `view.hand` = **手牌**（`cards.yml`）、`view.shelf` = **货架**（`card_store`）；`view.cards` 保留为 `hand` 的旧名 |

### 8.2 8 个函数的用法

核心库 8 个函数在 GUI 里的用法（详见《核心库调用说明.md》）：

| GUI 动作 | 调用 | 要点 |
|---|---|---|
| 启动页填列表 | `list_saves()` | 只显示 `is_primary=True` 的，其余进"历史存档"组 |
| 打开存档 | `open_save(save_id)` | 失败抛 `FileNotFoundError` ⇒ 提示"存档已被移动或删除" |
| 切页 / 刷新 | `save.view(catalog=cat)` | `cat` 给 `max_st` / `max_spec`；**必须给**，否则战力上限显示不出来 |
| 算能力位 | `save.capabilities()` | `can_edit_*` 决定控件启用；`unavailable_reason()` 给 tooltip |
| 滚轮改值 | **不调核心库**，只改内存 pending | 核心库是**写盘**用的，不是"编辑态" |
| 点「应用更改」 | `save.plan_edit(edits, catalog=cat)` | `plan.ok == False` ⇒ 禁用确认框的「应用」 |
| 确认框 | `validate(plan)` | 第二道防线；失败同样禁用「应用」 |
| 确认后 | `save.commit(plan)` | 成功 ⇒ Toast + 备份路径；**失败必须说"原存档未改动"** |
| 写回后 | **重新 `save.view()`** | 提交会清缓存，不重读会显示旧数据 |
| 点「撤销」 | `save.undo()` | 按钮可用性看 `save.undo_available()`，文案看 `save.undo_peek()` |
| 下拉框数据 | `catalog.units()` / `spec_types()` / `card_types()` / `hq_types()` / `fronts()` | 只做**候选**，不是白名单 |
| 商店补全 | `catalog.store_defaults(campaign, front, conference)` | 只在"新增商品"时用 |

**统一原则（来自核心库规范，GUI 不得违背）**：

1. **GUI 永远不直接读写存档文件** —— 只经核心库；
2. **GUI 不自己判断"能不能改"** —— 只经 `capabilities`；
3. **GUI 不吞错误** —— 核心库返回的 `errors` 全部要显示，不能只弹一个"操作失败"；
4. **不往存档塞自定义字段**（`PREVENT_EXTRA`）；
5. 改完立刻重新 `view()`。

## 10. 技术实现

### 10.1 运行时：给随包 Python 补 tcl/tk

**【实证】** 随包的 `python/` 是 **embeddable 版 CPython 3.14.3，**没有** `tkinter`**
（`import tkinter` → `ModuleNotFoundError`）。要做原生窗口必须补齐。

补齐清单（**全部来自本机已有文件，不联网**）：

| 文件 | 落位 | 来源 | 体积 | 作用 |
|---|---|---|---|---|
| `_tkinter.pyd` | `python/` | 游戏 `lib\`（CPython 官方 3.14 构建） | 69 KB | C 扩展 |
| `tcl86t.dll` | `python/` | 游戏 `lib\` | 1.84 MB | Tcl 8.6 运行时 |
| `tk86t.dll` | `python/` | 游戏 `lib\` | 1.59 MB | Tk 8.6 运行时 |
| `zlib1.dll` | `python/` | 游戏 `lib\` | 146 KB | **`tcl86t.dll` 的依赖，缺了 DLL 加载必失败** |
| `tkinter/`（含 `ttk.py`） | `python/Lib/site-packages/` | 系统 Python 3.14.7 的 `Lib\tkinter` 源码包 | ~250 KB | 纯 Python 层 |
| `tcl8.6/` | **`lib/`（包根）** | 游戏 `share\tcl8.6` | 3.0 MB | Tcl 脚本库（`init.tcl` 等） |
| `tk8.6/` | **`lib/`（包根）** | 游戏 `share\tk8.6` | 1.6 MB | Tk 脚本库（`tk.tcl` 等） |

合计 **+8.7 MB**（22.5 MB → 31.2 MB）。

**【实证】** 脚本库**必须放在 `<包根>/lib/`**，不能放在 `python/` 下面 ——
Tcl 的自动发现路径是 `<prefix>/lib/tcl8.6`、`<prefix>/library`、`<prefix>/tcl8.6.15/library`，
而 embeddable runtime 的 `<prefix>` 是**包根**（`python/` 的上一级），不是 `python/` 本身。
实测三种布局：

| 布局 | 不设环境变量 | 结论 |
|---|---|---|
| `python/Lib/tcl8.6` | ❌ `Can't find a usable init.tcl` | prefix 不是 `python/` |
| `python/tcl8.6` + `TCL_LIBRARY` | ✅ | 靠环境变量才work |
| **`<包根>/lib/tcl8.6` + `<包根>/lib/tk8.6`** | ✅ **不需要任何环境变量** | **采用这个** |

**【决策】** 采用第三种布局 —— **零环境变量依赖**。
另外 `run.bat` / `run_tests.bat` 里**也**显式设 `TCL_LIBRARY` / `TK_LIBRARY`（指向 `%~dp0lib\tcl8.6`），
作为"整包被挪位置"时的兜底；GUI 入口在 `import tkinter` 之前也会自己设一次。

**【实证】** 端到端验证通过（`docs/证据脚本/e144_tktest.py` + 仓库内实测）：

```
python: 3.14.3
  TkVersion const: 8.6 TclVersion const: 8.6
  Tk() OK  patchlevel: 8.6.15
  windowingsystem: win32
  themes: ('winnative', 'clam', 'alt', 'default', 'classic', 'vista', 'xpnative')
  clam OK
  PhotoImage OK
  lib E:/.../uoc2-save-modifier/lib/tcl8.6      ← 自动发现，无环境变量
```

**注意事项**：

* 游戏的 `lib\tkinter` 是**冻结版**（只有 `__init__.pyc`，**没有 `ttk.py`**）⇒ 必须用系统 3.14.7 的**源码包**；
* `_tkinter.pyd` 依赖 `python314.dll` ⇒ 必须与随包 runtime 的 Python 次版本一致（3.14.x 补丁版 ABI 兼容，已验证）；
* `_tkinter.pyd` / `tcl86t.dll` / `tk86t.dll` 都是 CPython / Tcl / Tk 的官方组件，
  **可再分发**（PSF / BSD 风格许可）。
* ⚠️ **Tcl 对非 ASCII 路径不友好**（报错信息里中文路径会被按本地代码页显示成乱码）——
  但这只是**报错信息**的显示问题，脚本库本身能被正确定位与加载（已验证 `info library` 输出正常）。

### 10.2 PNG 缩放管线（纯标准库）

**问题**：Tk 8.6 的 `PhotoImage` 能读 PNG（含 alpha）✅，但**只能整数倍 `subsample`**（最近邻，缩到 1/4 会糊成一团）❌。
随包 Python **没有 PIL**。

**方案**：写一个 ~250 行的纯标准库管线（`zlib` + `struct`）：

```
PNG 文件
  → 解码（IHDR/IDAT/PLTE、5 种滤波器反滤波）        ← 已验证可行
  → 缩放（双线性 + alpha 预乘，避免透明边缘发黑）
  → 重新编码 PNG（zlib 压缩 + CRC32）
  → PhotoImage(data=base64.b64encode(png))
```

**【决策】** 用**双线性 + alpha 预乘**（不是最近邻）：游戏立绘有大量半透明边缘，
最近邻缩放会出现锯齿和黑边。

**缓存**：LRU，键 = `(路径, 目标宽, 目标高)`，上限 **200 张 / 48 MB**。
同一张图常被列表和详情同时用（不同尺寸）⇒ 缓存命中率高。

**性能**：实测需控制在 **单张 < 80 ms**。列表滚动时按需解码，**只解码可见行**。

**兜底**：解码失败（未知色彩类型、损坏文件）⇒ 画一个 `border` 色圆角方块 + 类型首字母，**不崩**。

| 议题 | 选择 | 理由 |

### 12.6 血量两层逻辑 ✅ 已定（用户补充）

**决定**：血量不是一个数，是**两层**：

```
tot_st = act_st + sup_st      （当前血量 = 未被压制 + 被压制）
```

* 上限 `max_st` 来自类型表；
* **数字区滚轮调 `tot_st`** —— `sup_st` 不变，`act_st` 变；
* **血条本体滚轮调 `sup_st`** —— `act_st` 不变，`tot_st` 变。

写盘时生成**两条** `Edit.unit_field`（`act_st` 与 `sup_st`）。
合计超 `max_st` 是**软警告**（`handlers.py:145`），不阻断。

> 用户原话：「当前血量和当前未被压制血量（未被压制和压制的血量之和为当前血量），所以说我们是不是弄两层逻辑。」
