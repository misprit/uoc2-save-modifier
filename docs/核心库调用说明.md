## 0. 三十秒上手

```python
from save_modifier_core import list_saves, open_save, Edit, validate

# 1) 列存档
for info in list_saves():
    print(info.save_id, info.display_name)

# 2) 打开
save = open_save("campaigns/west.usg")

# 3) 看当前状态（能力位驱动 GUI 的启用/禁用）
view = save.view(catalog=None)
if view.capabilities.can_edit_units:
    for u in view.units:
        print(u.id, u.display_name, u.xp)

# 4) 规划（不碰磁盘）
plan = save.plan_edit([Edit.unit_field(1, "xp", 300)])
if not plan.ok:
    print(plan.errors)
else:
    print(plan.notes)          # 人话："单位 1 的 xp：10 → 300"
    print(validate(plan).ok)   # 第二道防线

    # 5) 提交（备份 → 校验 → 原子替换，并压撤销栈）
    res = save.commit(plan)
    print(res.ok, res.backup)

    # 6) 不满意就撤（撤销前会校验基准，过期就拒绝）
    save.undo()
```

**核心库只依赖标准库 + PyYAML**，不 import tkinter、不启子进程、不碰游戏进程。

## 2. 8 个对外函数（§0.2 冻结版）

### 2.1 `list_saves(paths=None, *, include_archived=True) -> list[SaveInfo]`

扫描 `%LOCALAPPDATA%\.uoc2\save\` 下的**全部**存档，按最后修改时间**倒序**返回。

⚠️ **游戏自己只读 `campaigns` 与 `games` 两个目录**；存档根下其它目录都是
**玩家自建的归档区**（目录名叫什么都行）⇒ 修改器照样读，用 `archived` 标记区分。

```python
@dataclass(frozen=True)
class SaveInfo:
    save_id: str          # 相对存档根目录的 posix 路径，如 "campaigns/west.usg"
    path: Path            # 绝对路径
    kind: str             # "campaign" | "standalone"
    archived: bool        # 在玩家自建的归档目录里？（游戏不认的位置）
    is_primary: bool      # 是"当前存档"吗（备份/副本为 False）
    campaign_id: str | None
    campaign_name: str | None     # 战役名的**本地化键**（如 id_campaign_name_c_stalingrad_p_dlc4）
                                 # —— 中文名要用 `locale` 查，别自己猜（实测 → 「斯大林格勒」）
    scenario: str | None          # 当前战斗的场景 id
    standalone_scenario: str | None
    mtime: float
    size: int
    # 派生属性
    name: str             # 不含扩展名的文件名
    display_name: str     # 给玩家看的名字（已含"战役 ·"/"独立场景 ·"标注）
    is_standalone: bool
```

> **GUI 提示**：只显示 `is_primary=True` 的；备份/副本单独列一组。

### 2.2 `open_save(save_id, paths=None) -> Save`

`save_id` 用 `list_saves()` 给的 `save_id`（或直接给绝对路径）。
找不到会抛 `FileNotFoundError`。

```python
with open_save(info.save_id) as save:      # 记得 close（with 最省心）

```

### 2.3 `save.view(catalog=None) -> View`

给 GUI 用的**只读投影**。`catalog` 给了才会填 `max_st` / `max_spec`
（战力上限在**类型定义**里，不在存档里 —— §5.3）。

```python
@dataclass
class View:
    save: SaveInfo
    capabilities: Capabilities   # 8 个能力位（见 §3）
    stage: str                   # 显示文本：战斗中（第 N 回合）/ 会议界面（已发牌）/ …
    prestige: int | None
    score: int | None
    units: list[UnitView]
    hqs: list[HqView]
    hand: list[CardView]         # ★ 手牌 = 根 cards.yml（你手里已经拿到的牌）
    shelf: list[CardView]        # ★ 货架 = 根 main.yml.card_store（会议里能买的牌）
    store: list[StoreEntryView]
    battle_turn: int | None
    warnings: list[str]          # 该存档的注意事项，直接显示给玩家

    @property
    def cards(self): ...         # `hand` 的旧名（保留是为了不打断已有调用方）
```

> ⚠️⚠️ **手牌与货架千万别搞反**（2026-11-18 修正 —— 核心库原先正好反了）：
>
> | | 来源 | 是什么 | 张数上限 |
> |---|---|---|---|
> | **`hand`** | 根 `cards.yml` | **手牌** —— 已经拿到手里的牌 | `card_deck_limit`（classic = 4） |
> | **`shelf`** | 根 `main.yml.card_store` | **货架** —— 会议界面里可以买的牌 | `card_store_limit`（恒为 5） |
>
> 旁证：实测存档（classic）手牌正好 **4** 张、货架正好 **5** 张。
> 游戏侧 `BuyCard.do` 是 `card_store.pop(position)` → `campaign.add_card(...)`
> ⇒ `card_store` 是**买的地方**，`cards.yml` 是**放牌的地方**。
>
> ⚠️ `view.hand` / `view.shelf` 在 **GUI 里叫「手牌区」和「货架区」**，
> 和 §7.5 的卡牌页布局一一对应。

各条目的字段：

```python
UnitView:  id, type, name_brief, name_full, hq_id, xp, act_st, sup_st,
           specs: tuple[dict,...], uv, entr, supply, ap, losses, retreated,
           in_roster: bool, max_st: int|None, max_spec: int|None
           # 派生：total_st（活跃+压制）、display_name
HqView:    id, name_brief, name_full, general, force_pool: tuple[dict,...],
           cp, max_cp, supply, uv, xp, xp_target, branch_levels,
           branches: dict|None,          # ★ 技能树 {分支: [{action,cost,level,sp_avail,sp_used}]}
           persistent, overrun, turn_disbanded
           # 派生：display_name、branch_tiers（{分支: {级别 tier: [技能…]}}）
CardView:  card_type, is_free, position, unit_id, used
StoreEntryView: front, sub, equipment, spec, nationality, price, quantity
           # sub = "store"（普通）| "elite_store"（精英）—— store.yml 是两层结构
           # 派生：what（= spec 或 equipment）、is_elite
```

> ⚠️ `view.stage` **只用于显示**，**不得**用来决定改哪张表 —— 那是能力位的活。
>
> ⚠️⚠️ **总部的 `level` 有两个意思**（`e165`，U12）：
>
> | | 字段 | 含义 |
> |---|---|---|
> | **分支生效等级** | `branch_levels[分支].level`（0–3） | 这个分支**当前生效到哪一级** |
> | **分支被压制** | `branch_levels[分支].suppressed`（**整数** 0–3） | **被压住的级数**（**不是布尔开关**）；游戏内部「解锁到几级」= `level + suppressed`（`e166`） |
> | **级别 tier** | `branches[分支][i].level`（1–3） | 这条技能在游戏内矩阵的**第几列** |
>
> `HqView.branch_tiers` 把技能按 **tier** 分好组，直接拿来画「分支 × 级别」矩阵；
> **tier ≠ 分支等级**，别混。

### 2.4 `save.plan_edit(edits, catalog=None) -> Plan`

**不碰磁盘。** `edits` 是一组 `Edit`（结构化，**不接受 YAML 文本**）。

```python
@dataclass
class Plan:
    save_id: str
    path: Path
    changes: list[FileChange]     # 每个被改条目
    notes: list[str]              # 一行行的人话说明（GUI 主视图用这个）
    errors: list[str]
    warnings: list[str]
    ok: bool                      # = not errors
    changed_entries: list[str]
    summary: str

@dataclass
class FileChange:
    entry: str        # ZIP 内条目名，如 "units.yml"
    layer: str        # "L1" 或 "L3"（L3 只可能是战区资产那一个例外）
    before: str
    after: str
    diff: str         # unified diff
    notes: list[str]
    is_l3_exception: bool
```

**`plan.ok` 为假就绝对不能提交**（`plan.errors` 里有原因）。

### 2.5 `validate(plan) -> ValidationResult`

对计划做**第二遍独立复核**（规划时已经查过一遍，这里再查一次，防止任何路径绕过校验）。

```python
@dataclass
class ValidationResult:
    ok: bool
    errors: list[str]
    warnings: list[str]
    summary: str
```

### 2.6 `save.commit(plan) -> CommitResult`

写回。顺序**固定**，一步都不能省：

1. **备份** —— `<存档名>_BACKUP.usg`（同名已存在就 `_BACKUP_2`…，**绝不覆盖**）
2. **写临时文件** —— 按原存档的条目清单与顺序重建，元数据沿用原存档
3. **校验** —— 逐条 SHA256 比对，确认**只有计划里那几个条目变了**
4. **原子替换** —— `os.replace`

任何一步失败都**完整回滚**：原存档一个字节都不动。
成功后还会把本次改动**压进撤销栈**。

```python
@dataclass
class CommitResult:
    ok: bool
    nothing_to_do: bool     # 计划里没东西可改（不是错误）
    path: Path | None
    backup: Path | None
    changed: list[str]      # 实际变了的条目
    errors: list[str]
    warnings: list[str]
    report: PackReport | None
    summary: str
```

### 2.7 `save.undo() -> UndoResult`

修改器**自己的**撤销栈（与游戏内「重置会议」是两套独立机制）。

* 粒度 = **一次 commit**（一次改了 3 个单位就一起撤）
* 栈**落盘**在存档旁边的 `<存档名>.undo.json`（游戏只扫 `*.usg`，不冲突）
* 撤销前**重新校验基准**：当前内容必须等于记录里的"改后哈希"；
  对不上（多半是玩家在游戏里手动改过）⇒ **拒绝执行并说明原因**，不硬改
* 撤销走的是**和 commit 完全相同**的写回管线（也会再生成一份备份）

```python
@dataclass
class UndoResult:
    ok: bool
    nothing_to_do: bool     # 栈是空的
    path: Path | None
    backup: Path | None
    restored: list[str]
    errors: list[str]
    warnings: list[str]
    summary: str
```

辅助（8 个函数之外，但 GUI 需要它们决定按钮是否可点）：

```python
save.undo_available() -> bool     # 栈里有没有东西可撤
save.undo_count() -> int          # 栈里有几条记录（G1 的 Rail 显示「撤销栈 N 条」）
save.undo_peek() -> str | None    # "可撤销：改了 1 个文件：单位 1 的 xp：314 → 77"
```

### 2.8 `catalog.*` —— 下拉框数据源

**只做候选，绝不做白名单**（§9.1.3）。

```python
from save_modifier_core import catalog

catalog.units()        # list[str]  627 个单位类型
catalog.hq_types()     # list[str]  213 个总部类型
catalog.card_types()   # list[str]  39 个卡牌类型
catalog.spec_types()   # list[str]  375 个特种兵类型
catalog.fronts(campaign_id) -> list[str]   # 某战役包的战线名
catalog.store_defaults(campaign_id, front, conference) -> list[dict]
```

也可以直接用 `Catalog` 类（要拿 `max_st` / `spec_cap` 时用这个）：

```python
cat = Catalog(CorePaths.discover())
cat.max_st("us_inf_42")      # 6
cat.spec_cap("ger_inf_39")   # 2 = min(3, max_spec)
cat.step_icon("us_arm_42")   # "step_armor_2"  ← 战力阶梯图标名
```

#### 特种兵侧的四个新读能力（2026-11-18 · U10 / U11 补齐）

> 备选池每一格要显示**中文名 + 攻防装甲火力 + 特殊类型**，
> 还要判断**能不能挂**、**本战役有没有** —— 这四件事全在**游戏包里**，不在存档里。

```python
from save_modifier_core import catalog

catalog.spec_type("us_recon_42")
# SpecialistType(name='us_recon_42', faction='allies', nationality='us',
#                attack=7, defense=4, armor=1, artillery=0,
#                flags=('recon',), ...)      ← 数值全在游戏包，存档里只有引用

catalog.nationality("italian")
# Nationality(name='italian', faction='axis',
#             parent_nationality='german', ...)   ← 父国籍决定「能不能挂」

catalog.campaign_specialist_pool("west")
# set[str]，45 个  ← 「本战役默认池」= 商店 spec: ∪ 场景 units.yml 的 specs[].type

catalog.specialist_candidates("us_arm_42", "west")
# ([...9 个...], 'campaign')
catalog.specialist_candidates("us_arm_42", "berlin")
# ([...23 个...], 'empty_intersection')   ← 敌国单位 → 自动放宽
catalog.specialist_candidates("us_arm_42", None)
# ([...23 个...], 'no_campaign')          ← 找不到战役包 → 自动放宽
```

**口径标签**（第二个返回值）—— GUI 照它决定提示文案：

| 标签 | 含义 | UI 表现 |
|---|---|---|
| `campaign` | 战役默认池 ∩ 游戏规则 | 池标题写明「XX 战役默认」+ 种数 |
| `no_campaign` | 找不到战役包 | 提示「未找到战役包，已显示全部可挂项」 |
| `empty_intersection` | 该单位与战役池交集为空（敌国单位） | 提示「本战役无对应特种兵，已显示全部可挂项」 |

**挂载规则本身**也搬进核心库了 —— **GUI 不要自己写一遍**：

```python
cat.spec_can_attach("ger_arty_40", "ita_alp_39")   # True（意大利的父国籍是德国）
cat.spec_can_attach("us_recon_42", "sov_inf_41")    # False（阵营都不同）
```

逐条复刻游戏自己的 `_can_add_specialist_no_len`（`e162` 字节码实证）：
阵营必须相同；国籍相同，**或单位国籍的 `parent_nationality` == 特种兵国籍**；
`captured=True`（被俘获的牌）跳过这两项。
⚠️ 槽位容量（`len(specs) < max_spec`）是**另一个**判定，不在这个函数里。

> **⚠️ 性能**：`campaign_specialist_pool()` 要扫该战役的所有会议 + 所有场景
> （实测 base/west ≈ **170 ms**）⇒ 核心库**按战役缓存**，
> 但**别在滚动路径上反复调** —— GUI 打开单位页时取一次就够。
>
> **⚠️ 数据源**：国籍表在 `entity_types/nationalities.yml`（base 包 40 个）
> + `nationalities_2.yml`（给 mod 用的空模板）——
> 这两个是**文件**不是目录，所以**不走** `entity_types/<目录>/` 那套目录索引。
> 用户包优先（与类型表同样的「先到先得」语义）。

### 2.9 `catalog.card_whitelist(save)` —— 卡牌商店白名单

**GUI 的卡牌页必须用它**来算"哪几张卡可以上架"（规范 §7.5.1）。

```python
wl = cat.card_whitelist(save)
wl.allowed            # frozenset[str] —— 可以上架的卡牌类型名
wl.blocked            # dict[str, str] —— 被屏蔽的卡 → 中文原因（可直接显示）
wl.is_allowed("truck_axis")    # bool
wl.reason("air_attack_allies") # "阵营 allies ≠ 玩家 axis"；没被屏蔽返回 None
wl.player_faction     # "axis"
wl.conference         # "c_40_06"
wl.probabilities      # dict[str, float] —— 本次会议的 meta_type 概率表
```

规则 = 逐条复刻游戏的 `Campaign.get_cards_probabilities`（`e160` 实证）：

```
可上架 = { ct : ∃ meta_type, p(meta_type) > 0,
             ct.faction == 玩家阵营,
             (¬ct.has_unit)                      ← 不召唤单位 ⇒ 无条件可上架
             OR ( ct ∈ card_type_units          ← 本战役登记过 ⇒ 有单位可召唤
                  ∧ ct ∉ used_card_types_with_unit
                  ∧ ct ∉ 当前手牌
                  ∧ (预留单位不存在 OR 未阵亡) ) }
```

* **白名单是"当前存档 + 当前会议"的状态** ⇒ **每次开卡牌页重算，不要缓存**；
* 核心库**自己也会校验**（`card_store_set` / `card_store_add` 写盘前再查一遍），
  不能只靠 GUI 挡。

#### `UnitType` 的字段（2026-11-18 扩充）

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | `str` | 类型名 |
| `faction` / `nationality` | `str \| None` | 阵营 / 国籍 |
| `movement` | `str \| None` | `infantry` / `mobile` / `cavalry` / `mountain` |
| `attack` / `defense` / `armor` | `int \| None` | 基础属性 |
| **`max_st`** | `int \| None` | **战力上限**（上限在类型定义里，不在存档里） |
| `max_spec` | `int \| None` | 特种兵上限；`None` = 该类型没这个字段 |
| **`equipment`** | `str \| None` | **装备类别**（`None` = 无装备） |
| **`equipment_q`** | `int \| None` | **装备档位**（0 = 无装备） |
| `name_brief` | `str \| None` | 本地化 id |
| `spec_cap` | `int`（属性） | `min(3, max_spec or 3)` |
| **`step_icon()`** | `str`（方法） | **战力阶梯图标文件名**（不含目录与扩展名） |

**`step_icon()` 的规则**（游戏自己的 `hq_ctrl.pyc::HQCtrl._fp_helper` 字节码实证）：

```python
'steps/step{}'.format('_' + equipment + '_' + equipment_q if equipment else '')
```

| 类型 | `equipment` / `equipment_q` | `step_icon()` |
|---|---|---|
| `us_inf_42` | `None` / `0` | `"step"` |
| `us_arm_42` | `armor` / `2` | `"step_armor_2"` |
| `ger_pz_dlc7` | `armor` / `2` | `"step_armor_2"` |

⇒ GUI 拿 `cat.step_icon(type)` 拼成 `assets/surfaces/steps/<名字>.png` 即可。
**先判 `equipment` 真假，再拼 `equipment_q`** —— 游戏就是这么拼的（`equipment` 为 null 时 `equipment_q` 恒为 0，
不会拼出 `step__0`）。

### 4.1 ⚠️ 几个容易踩的语义

**① `unit_id` 不是"名册里任意一个单位"**

带单位的卡（`has_unit: true`）的 `unit_id`，真实语义是
**`document/main.yml.card_type_units` 里为这张卡登记的预留 id**。
实测 blitzkrieg 的 `tactical_para_german` → `718`（名册里的 `ger_fsjg_40`），
而 718 **此刻还不在存档 `units.yml` 里**（还没被召唤过）——
所以"在名册里"那条只是碰巧成立，**语义是错的**（2026-11-18 已改）。

⇒ `Edit.card_add("tactical_para_german")` **不用传 `unit_id`**，
核心库会自动补上预留 id；传错了会**硬拦**（填错 ⇒ 召唤出错误的单位）。

**② 总部的「技能专精次数」和 `cost` 是一对**（`e165`）

存档里 `branches[分支][i].cost` 存的是**已经扣掉专精减免**的 CP 消耗
⇒ **原始 CP = `cost + sp_used`**。
只写 `sp_used` 不动 `cost` ⇒ 存档自相矛盾（游戏读到的 CP 会比该技能实际贵）。

⇒ `Edit.hq_branch_sp(hq_id, branch, action, sp_used)` **自动同步 `cost`**，
调用方只管给 `sp_used`；`sp_avail` 为空的技能（兵库四动作 + `motor_pool`）
会**硬拦**（它们本来就没有技能点）。

**③ `is_free` 在两处含义完全不同**

| 位置 | `is_free` 的作用 | 改了会怎样 |
|---|---|---|
| **货架**（`card_store`） | **真实价格**：True ⇒ 价格 0（不扣声望）；False ⇒ 价格 = 卡的 `cost` | 真实影响 —— 把付费卡改免费 = 白嫖 |
| **手牌**（`cards.yml`） | **没有玩法影响** —— 只改 tooltip 文案与卡背贴图 | 只是"来源标记" |

⇒ GUI 上货架的开关要标当前状态（"改成免费"/"改成收费"），
手牌的开关要说明它**只影响显示**。

**④ 总部的「被压制等级」不是开关，是被压住的级数**（`e166`）

`branch_levels[分支] = {level, suppressed}`：

* `level` = **当前生效**的等级（0–3）；
* `suppressed` = **被压制的等级数**（**整数** 0–3，**不是布尔**）；
* 游戏内部「**解锁到几级**」= **`level + suppressed`**
  （`can_add_branch_level` 就是这么算的，`current_level == 3` 就不许再加）。

⇒ `Edit.hq_branch_suppressed(hq_id, branch, n)` 压 N 级时**真实等级不变**，
核心库自动重算：

    新 level = (旧 level + 旧 suppressed) − 新 suppressed

（等价游戏自己的 `branch_suppress`：生效等级 −N、被压数 +N）。
校验：压制数**不能超过**该分支总等级；`level + suppressed` **不能超过 3**。

⚠️ **压制只写在「战役进行中」的存档里才有意义** —— 游戏在一局结束时
（`set_end_game` → `unsuppress_branch_levels`）会把压制**全部还原**；
从会议阶段进战役也会重置。

**⑤ 补给卡车数 = 总部补给作用范围，改它不扣声望**

`hqs.yml` 的 `trucks` 是**整数**；合法值 **1–5**（**0 不行** —— 总部至少要有一辆）。
1–5 辆依次对应补给作用范围 **5 / 8 / 10 / 11 / 12** 格
（游戏 `game.yml` → `supply_hubs_ranges = [5, 8, 10, 11, 12]`）。

⇒ 用 `Edit.hq_trucks(hq_id, n)`，**不要**用 `hq_field(hq_id, "trucks", n)`
（后者没有 1–5 校验，摘要里也不会带「补给作用范围 N 格」）。
这个操作**完全不动 `main.yml`** ⇒ **不涉及声望**。

> ⚠️ **一处对不上（照实记 · `e166`）**：游戏字节码 `HQState/mp_movement` 用的是
> **0-based** 下标 `supply_hubs_ranges[self.trucks]`（trucks=3 → 11 格），
> 而游戏内 UI 的 5 个图标按 5/8/10/11/12 排开 ⇒ **两者差一格**。
> **本工具按用户口径 + 游戏内画面取 1-based**，存档里仍然**只写 `trucks` 这一个整数**。

**明确不支持**（会报错，不是静默忽略）：

| 想做的事 | 结果 |
|---|---|
| `Edit.unit_field(id, "type", ...)` 改编制 | 报错并给替代建议（改战力 / 特种兵） |
| 新增单位 / 新增单位类型 | **没有这种 Edit** —— 要写只读层，游戏内回退不掉 |
| 改登陆进场特种兵 | **没有这种 Edit** |
| 跳到某会议 | **没有这种 Edit** |
| 改 `milestones` | **没有这种 Edit** —— 改了也是"改了却像没改" |

### 4.1b CP 的合法范围是**硬范围**（U19 · 游戏字节码取证）

`Edit.hq_field(hq_id, "cp", v)` 与 `Edit.hq_field(hq_id, "max_cp", v)`
**超范围会被硬拦**（`errors`，不是 `warnings`）：

| 字段 | 合法范围 | 依据 |
|---|---|---|
| `cp`（**当前** CP） | **0 – 9** | `state/constants.pyc`：`hq_max_cp = 9`；`data_validation/hq.pyc`：`All(int, Range(min=0, max=hq_max_cp))` |
| `max_cp`（**CP 上限**） | **3 – 9** | 同上：`All(int, Range(min=hq_min_max_cp, max=hq_max_cp))`，`hq_min_max_cp = 3` |

⚠️ **为什么必须硬拦**：游戏用 voluptuous 校验存档 schema，
**超范围 ⇒ 校验失败 ⇒ 存档直接打不开** ——
不是「显示异常」，是**把存档搞崩**。

⚠️ **两个字段要分清**：
`cp` = **当前剩余** CP（这一局还能花多少），
`max_cp` = **该总部的 CP 上限**（每回合回满到多少）。
GUI 上是两个**独立可调**的数字（§7.4.1a）。

跨字段**警告**（不拦，游戏读档时按上限截断）：

* `cp` 超过该总部的 `max_cp` ⇒ 警告「游戏读档按上限截断」；
* `max_cp` 降到低于当前 `cp` ⇒ 同样警告。

⇒ GUI 上应当**在滚轮时就夹到边界**，根本不让用户产生非法值。

### 4.2 软警告 vs 硬拦

| 情况 | 行为 |
|---|---|
| 能力位不满足 | **硬拦**（`plan.errors`） |
| 值越界（xp > 400 等） | **硬拦** |
| 战力超过类型的 `max_st` | **软警告**（`plan.warnings`），照写 |
| 特种兵类型不存在 | **硬拦** |
| 特种兵数量超过 `min(3, max_spec)` | **硬拦** |
| 商店 `quantity` 设成 0 | **硬拦**（游戏没有售罄标记，下架要删条目） |
| 卡车数不在 1–5（**0 也不行**） | **硬拦** |
| 压制数不是整数 / 超过该分支总等级 / `level + suppressed > 3` | **硬拦** |
| 改的是战斗外会被重算的字段（`uv`/`entr`/`supply`/`ap`） | **软警告** |

## 5. GUI 的标准五步

```
1. list_saves()            → 填存档下拉框（只列 is_primary）
2. open_save(id)           → 拿到 Save
3. save.view(catalog)      → 填表格；用 capabilities 决定哪些按钮可点
4. save.plan_edit(edits)   → 填变更清单（plan.notes）+ diff 面板
   ├─ plan.ok == False     → 显示 plan.errors，不给"保存"按钮
   └─ validate(plan)       → 第二道防线
5. save.commit(plan)       → 成功提示 + 备份路径；之后"撤销"按钮变可用
   └─ 玩家点撤销 → save.undo()
```

**写回后一定要重新 `save.view()`** —— 提交会清掉内部缓存的解析结果。

## 7. 错误处理约定

| 情况 | 表现 |
|---|---|
| 能力位不足 | `plan.errors` 里有中文原因（`caps.unavailable_reason`） |
| 值非法 | `plan.errors`（**不写盘**） |
| 存档在规划之后被别人改过 | `commit` 报错拒绝写入（别把人家的改动覆盖掉） |
| 写回中途失败 | 原存档一个字节都不动（临时文件丢弃） |
| 撤销基准过期 | `undo` 报错，**拒绝执行**，并提示可以复制 `_BACKUP.usg` 回退 |
| 撤销栈文件损坏 | `undo` 报错并说明（**不静默吞掉**） |

**核心库不抛"业务异常"** —— 校验类问题全部走 `errors` 列表；
只有真正unexpected的情况（文件不存在、存档损坏）才抛异常。

## 8. 已知边界

* **独立场景存档没有商店、没有卡牌** —— 能力位会把这块整个禁用。
* **战区资产只能在战斗里改** —— 战斗外改会被场景重算覆盖（这是"改了却像没改"）。
* **改名直接写明文**（写进 `name_brief` / `name_full`）—— 不写 temp mod，不写本地化包。
  游戏会正常显示。
* **`type`（编制）不可改**。
* **总部的技能树在 `branches`**（不是 `branch_levels`）——
  一个分支同一级最多 3 个技能，同一动作不能出现在两个分支（游戏自己校验）。
  `intel` 分支**恒为空**（455/455 个总部实测）⇒ 情报行没有技能。
* **技能图标取游戏原贴图**：`assets/surfaces/hq_upgrade/hq_upgrade_<action>_{off,on}.png`
  （140×140，20 个动作全覆盖）；`off` = 未解锁、`on` = 已解锁。
* **总部的「压制等级」不是开关** —— `suppressed` 是被压住的**级数**（整数 0–3）；
  真实等级 = `level + suppressed`，改压制要连带重算 `level`；
  游戏在一局结束（`set_end_game`）时会把压制**还原** ⇒ 只在「战役进行中」有意义。
* **补给卡车数 1–5** ⇒ 补给作用范围 5 / 8 / 10 / 11 / 12 格；
  **改它不扣声望**（不动 `main.yml`）。
* 撤销栈上限 20 条 / 32 MB，超了从最旧的开始丢。
* 撤销栈文件是 `<存档名>.undo.json`，**和存档放在一起** —— 玩家备份存档目录时记得一起带上。

### 4.1c 战区资产的三个字段（U20 · 游戏字节码取证）

`Edit.theater_asset()` 的三个字段**各自独立**，**不传就不改**：

```python
from save_modifier_core import Edit, UNSET

# 只改「当前可用」—— 另外两个保持存档里的原值
Edit.theater_asset("air_attack", to_use=3)

# 三个一起改
Edit.theater_asset("long_range_recon", to_use=2, uses_total=6, uses_turn=3)

# 把「本场景剩余」改成**无限**（None = 无限，**不是**「不改」）
Edit.theater_asset("air_attack", uses_total=None)

# 一个都不改 ⇒ 不产生任何写入（plan.changes 为空）
Edit.theater_asset("air_attack")
```

| 字段 | 含义 | 合法范围 | 越界后果 |
|---|---|---|---|
| `to_use` | **当前剩余可用次数** | **0 – ∞** | 负数 ⇒ 存档打不开 |
| `uses_total` | **本场景剩余总次数**（`None` = 无限） | **0 – ∞ 或 `None`** | 负数 ⇒ 存档打不开 |
| `uses_turn` | **每回合恢复次数** | **1 – ∞** | `0` ⇒ 存档打不开（`Range(min=1)`） |

⚠️ **为什么必须硬拦**：游戏用 voluptuous 校验存档 schema，
**超范围 ⇒ 校验失败 ⇒ 存档直接打不开** —— 不是「显示异常」，是**把存档搞崩**。

**跨字段硬不变式**：`to_use ≤ uses_total`（`uses_total` 有限时）。
⚠️ 这不是 UI 小讲究 —— 游戏每用一次资产就让 `uses_total` 减 1
（`Game.spend_theater_asset`），减成负数会让存档校验失败 ⇒ **存档打不开**。
核心库**硬拦**（进 `plan.errors`）；GUI 侧应当**自动夹取**，别让玩家提交了才报错。

**只警告不拦**的情况（游戏自己会按 `min()` / 重置处理）：

「回合开始后的**有效可用次数**」：

```
eff = uses_turn                (uses_total 为 None 时)
    = min(uses_turn, uses_total)   (uses_total 有限时)
```

| 情况 | 游戏的行为 |
|---|---|
| `uses_turn > uses_total`（有限时） | 回合开始按 `min(uses_turn, uses_total)` 恢复 ⇒ 实际每回合只能用 `uses_total` 次 |
| `to_use > eff` | 回合开始 `to_use` 被重置为 `eff` |

⚠️ GUI 请用**同一条 `eff` 公式**判断，别自己另写一套 —— 两边口径不一致，
玩家会在 GUI 里看着没事、提交时却被核心库拦下。

**UI 口径**（U21 拍板）：战区资产页的**主 X/X 取 `to_use` / `uses_total`** ——
这正是游戏自己显示的那两个数（`idp_super_tooltip_theater_uses_turn` + `_uses_total`）；
`uses_turn`（每回合恢复）**单起一行**，**同样可调**（游戏自己的卡牌、礼包、
官方场景编辑器都能改它 ⇒ 它本来就是玩家可影响的变量）。

**只改当前 phase 那一组**：`theater_assets` 在存档里**按 phase 分组**
（`[[phase0], [phase1], …]`），核心库读战斗 `main.yml` 的 `phase` 字段定位。
（U20 之前**永远改第 0 组**，phase ≠ 0 时会改错组。）

**跨字段不变式只此一条**：`to_use ≤ uses_total`（`uses_total` 有限时）。

**第四个字段 `to_use_not_used` 不暴露**：那是游戏内部的「上回合没用掉的结转池」，
核心库给玩家看不见，由游戏自己维护（`Game.theater_assets_start_turn` 写、
`Game.add_theater_asset_num` 消费）⇒ 不给 `Edit` 入口。

### 4.1c-2 战区资产的**全量候选**：加一项 / 删一项（U45）

存档里没有的资产也可以加，有的可以删。候选全集是**游戏自己的** 7 种
（`save_modifier_core.catalog.THEATER_ASSET_TYPES`，来源
`uoc2.state.constants.theater_asset_types`）：

```python
from save_modifier_core import Catalog, Edit

cat = Catalog()
for it in cat.theater_asset_universe():
    print(it["asset"], it["has_texture"])      # 7 种 + 有没有游戏原贴图

# 加一项：写全 5 个字段且自洽（to_use / to_use_not_used 由核心库算）
Edit.theater_asset_add("flying_artillery", uses_total=3, uses_turn=2)
# 加一项：无限（uses_total=None）
Edit.theater_asset_add("precision_bombing", uses_total=None, uses_turn=1)

# 删一项：删**整项**（不是把次数清零 —— 清零会留下永远用不了的死条目）
Edit.theater_asset_remove("air_attack")
```

**核心库硬拦**（进 `plan.errors`，磁盘不动）：

| 规则 | 说明 |
|---|---|
| `asset` 必须在那 7 种里 | 游戏的 `theater_asset_dict` 是 `Required('asset'): In(theater_asset_types)` ⇒ 写别的名字**存档打不开** |
| 当前 phase 那一组里不能有同名 | 游戏按名字取**第一个**匹配 |
| `uses_turn ≥ 1` | 游戏的 schema 是 `Range(min=1)` |
| 新增的 `uses_total` 是 `None` 或 **≥ 1** | 回合开始按 `to_use = min(uses_turn, uses_total)` 恢复 ⇒ `0` = **永远用不了**（用户说的「000 数据」） |
| 战斗外不能加 / 删 | 能力位 `can_edit_theater_assets`（= `in_battle`） |

**新增时写进存档的那一项**（5 个字段一次写全，且与游戏回合开始的口径一致）：

| 字段 | 怎么算 |
|---|---|
| `asset` | 玩家指定的资产名 |
| `uses_total` | 玩家填（`None` = 无限） |
| `uses_turn` | 玩家填（≥ 1） |
| `to_use` | `uses_turn`（`uses_total` 为 `None` 时）或 `min(uses_turn, uses_total)` |
| `to_use_not_used` | `uses_turn - to_use` |

⚠️ **只动当前 phase 那一组，组数不变**（实测所有存档恒为 2 组）——
改组数会让游戏的 `phase` 索引错位。
⚠️ **只对当前这场战斗生效**：场景自己的定义
（存档里的 `document/scenarios/<场景>/main.yml`）不动，
下一场战斗会按它重新初始化。

**只读对照**：「这场战斗本来有哪些战区资产」有两个来源，按优先级：

| 来源 | 取法 |
|---|---|
| 存档自带 | `Save.document_theater_assets()` → `{asset: {"uses_total":…, "uses_turn":…}}` |
| 游戏包 | `Catalog.scenario_theater_assets(scenario_id, campaign_id)` → 同上 |

### 4.1d 上架 / 加条目时，**特种兵的国籍自动跟着类型**（U22）

```python
from save_modifier_core import Edit

# 总部兵库加一条特种兵 —— **不用传 nationality**，核心库会自动填成类型国籍
Edit.hq_force_pool_add(5, {"quantity": 2, "spec": "ger_arty_40"})
# 写进存档的是：{"delay": 0, "nationality": "german", "quantity": 2, "spec": "ger_arty_40"}

# 商店上架一个特种兵 —— 同理，nationality 传类型国籍即可
Edit.store_add("south", "store", {
    "spec": "ger_arty_40", "nationality": "german",
    "price": 20, "quantity": 5,
})
```

**为什么是这样**：实测真实存档里 —— **商店 1043 条 + 兵库 1747 条** `spec` 条目，
国籍 **100% 等于该特种兵类型自身的 `nationality`，0 条例外**
⇒ 「国籍跟着类型走」是**游戏自己的规矩**，不是我们定的。

| 条目类型 | 国籍 | 原因 |
|---|---|---|
| **特种兵**（`spec`） | **自动填**，跟着类型 | 实测 2790 条 0 例外 |
| **装备**（`equipment`） | **要手选** | 装备与国籍是独立组合（实测 20+ 种：`infantry` × uk/us/german/…） |

⚠️ **自动填国籍需要游戏包**（`Catalog.spec_type()`）⇒
**GUI 必须把 `catalog` 传给 `plan_edit()`**：

```python
plan = save.plan_edit(edits, catalog=catalog)   # ← 别省这个
```

不传 `catalog` 时拿不到类型国籍 ⇒ 降级成**空国籍 + 一条警告**
（游戏读不出来，但至少不会静默写错）。

⚠️ 显式传了**与类型不符**的国籍 ⇒ **警告**（不硬拦）：
游戏自己的数据全是跟着类型走的，写不一致虽然游戏也能打开，但显示与行为会不对。

**GUI 侧的长相**（规范 §7.3.7「特种兵选择器」）：
商店上架与总部兵库加条目**共用一个组件**，直接复用单位页的
「备选池图标格 `.pcell`」+「已挂槽位卡 `.slot`」——
**选的时候就能看到攻 / 防 / 装甲 / 炮术和特性**，不用另外去查。

### 4.1e 重复条目：**商店 / 兵库都不能重复**（U23）

两个新增入口都会**硬拦**重复条目 —— 判重范围和判定键**两处不同**：

| 入口 | 判重范围 | 判定 | 重复了怎么办 |
|---|---|---|---|
| `Edit.store_add(front, sub, entry)` | 单个 **(战线, 子商店)** | **任何**重复（价格 / 库存不同**也算**） | 进 `plan.errors`，上架失败 |
| `Edit.hq_force_pool_add(hq_id, entry)` | 单个**总部**的 `force_pool` | **同身份 + 同延迟**（**延迟不同可以共存**） | 进 `plan.errors`，添加失败 |

**条目的「身份」**：

```python
# 特种兵
("spec", "ger_arty_40", "german")
# 装备
("equipment", "infantry", "german")
```

⇒ **国籍算进身份** —— 同样是「德国步兵」，`german` 和 `uk` 是两样东西。

**为什么兵库允许「延迟不同」共存**：`delay` 是「这个部队等几个回合才能部署」，
游戏里就是合法机制 ⇒ 两个**延迟不同**的同种条目是**两批先后上线的部队**，不是重复。

**⚠️ 只拦新增，不校验存量**：
真实存档里商店有 **23 组**同身份重复（**完全相同 0 组**）、兵库有 **696 组**同身份重复
（其中 **393 组完全相同**）—— 那些是**游戏自己生成的数据**，
修改器**不动它们**，只是**不主动制造新的**。
改已有条目的数量 / 价格**不受影响**。

**⚠️ 商店判重不跨战线**：
多个前线的商店**库存彼此独立** ⇒ 在「意大利」有 `infantry/us`，
不代表「法国」也有 ⇒ 两边各自判重。

### 4.1f 兵库的「延迟」语义（U24 · 字节码取证）

**游戏的合并键 = `(delay, nationality, spec|equipment)`**
（`state/entities/force_pool.pyc::ForcePool.add`，延迟模式分支：
`_is_in` = 同 `(delay, nationality)`，`_same_data` = 同 `spec`/`equipment`，
命中就 `fp.quantity += quantity` 后 `return` —— **合并数量，不新建条目**）。

⇒ **同一个总部里，同身份 + 同延迟**不许并存；
⇒ **延迟不同可以共存** —— 那是**两批先后上线的部队**，
游戏按 `deploy_with_delay(N)` **逐批**部署（只取 `delay == N` 的条目）。

```python
# ✅ 可以：延迟不同 ⇒ 两条独立条目，分批上线
Edit.hq_force_pool_add(5, {"quantity": 2, "spec": "ger_arty_40", "delay": 0})
Edit.hq_force_pool_add(5, {"quantity": 2, "spec": "ger_arty_40", "delay": 2})
# → 核心库会给一条 warning：「延迟不同可以共存（游戏按延迟分批上线……）」

# ❌ 被拦：同身份 + 同延迟
Edit.hq_force_pool_add(5, {"quantity": 2, "spec": "ger_arty_40", "delay": 0})
# → errors：「同一个总部里不能有两条延迟同为 0 的同样条目」
```

**⚠️ 存量里可能有「完全相同」的两条**（同身份 + 同 0 延迟 + 同数量）：
游戏部署时会把它们合并（`_deploy_from_data` 按 delay 分组、组内同 spec 累加），
所以**不会出错**，但确实是「同一条被存了两遍」。
修改器**不主动制造新的**（只拦新增），也**不清理存量**。

**GUI 必须显示 `delay`** —— 它决定这条什么时候能部署；
并建议**按延迟分组**显示（游戏就是分批上线的）。

### 4.2 硬范围速查（不合规操作会被拦在哪）

**规则**：游戏用 voluptuous 校验存档 schema，**超范围 ⇒ 校验失败 ⇒ 存档直接打不开**
⇒ 核心库对每个可写字段都做了硬拦（进 `plan.errors`），不靠调用方自律。

| 字段 | 范围 | 入口 |

| `unit.xp` | 0 – 400 | `Edit.unit_field` |

| `hq.cp` / `hq.max_cp` | 0 – 9 / 3 – 9 | `Edit.hq_field` |
| `hq.supply` | **0 – 3** | `Edit.hq_field` |

⚠️ **同一条规则的多个入口必须一致** ——
`trucks` 能从 `hq_field` 和 `hq_trucks` 两条路改，
