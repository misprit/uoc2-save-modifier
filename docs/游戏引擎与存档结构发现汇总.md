## 1. 存档文件结构

### 1.1 `.usg` 是一层 ZIP，内层是 YAML + 少量二进制

* **【实证】** 存档 `.usg` 就是 ZIP（deflate）：**无目录条目**、**所有条目共用同一个时间戳**；
  内层文件全是 UTF-8 YAML（`.yml`），外加少量 NumPy `.npz` 二进制。
* **依据**：解包 → 重打包，954/954 个条目内容 SHA256 一致，`zipfile.testzip()` 通过。
* **对生成器的意义**：`.usg` 可以当普通 zip 处理；**条目顺序 = 游戏写入顺序**，但游戏用 .NET `ZipArchive`
  **按名字查找、不依赖顺序** ⇒ 自己写包时顺序可以自由，但**时间戳与 external_attr 要沿用原存档**。

### 1.2 分层：L0 游戏包 / L1 根表 / L2 检查点 / L3 战斗层 / L4 回合历史 / L5 战役文档

| 层 | 位置 | 是什么 | 可写？ |
|---|---|---|---|
| **L0** | `<game>/_packages/<dlc>/data/campaigns/<id>.usc/` | 游戏包里的战役模板（新建战役时当模板） | 只读（跨存档共享） |
| **L1** | 存档根目录 5 个 YAML：`main/units/hqs/cards/store` | 根状态，游戏每次读档都读 | ✅ **唯一可写层** |
| **L2** | `last_conference/`、`last_game/` | 检查点（玩家可回退的基线） | ❌ 只读 |
| **L3** | `games/<场景>/` | 当前战斗的实时状态 | ❌ 只读（**两个例外**见 §2.1） |
| **L4** | `games/<场景>/archive/<快照>/` | 逐回合历史 | ❌ 只读 |
| **L5** | `document/` | 战役包副本（战役名册等） | ❌ 只读 |

* **【实证】** 游戏内回退是**整表替换**：`_load_revert_campaign_data` 读检查点 `main.yml` →
  `self.__dict__.update(data)` → **清空 `units`/`hqs`** → 用检查点的 `units.yml`/`hqs.yml` 重新装载。
  ⇒ **只写 L1 才安全**：改 L2/L3/L4/L5 要么无效，要么把存档改成游戏自己造不出的状态。
* **【实证】** L5 的回退性质与 L2–L4 不同 —— **L5 不在任何检查点里**（实测 100 个检查点，0 个含 `document/`）
  ⇒ 写 L5 的改动**游戏内回退不掉**。

### 1.3 战役存档 vs 独立场景存档（目录名不一样）

* **【实证】** 战役存档 = 根 5 张 YAML + `document/` + `games/<场景>/`（可同时存在几十个）+ `last_conference/` + `last_game/`；
  独立场景存档 = 只有根 `main/units/hqs`（**无 `cards.yml`/`store.yml`**）+ `document/`（恰好 6 条目）+ **`game/`（单数！）**。
* **【实证】** 区分依据 = 根 `main.yml` 的 `standalone_scenario` 非空。
* **对生成器的意义**：独立场景存档**没有商店也没有卡牌** ⇒ 相关功能必须整个禁用（不是「没数据」）；
  场景预设只在游戏安装目录，存档里的 `game/` 是**运行时态**、不能当预设用。

### 1.4 五张 L1 表的字段边界（改设计前先看这张表）

| 表 | 能改 | 不能改（在游戏包里） |
|---|---|---|
| `units.yml` | `xp` / `act_st` / `sup_st` / `name_brief` / `name_full` / `specs`（挂载） | `type` 决定的 `max_st` / `max_spec` |
| `hqs.yml` | `cp` / `max_cp` / `supply` / `trucks` / `prisoners` / `branch_levels` / `branches` / `force_pool` | `template` 决定的分支解锁树 |
| `cards.yml` | 增删卡（`card_type` / `position` / `is_free` / `used`） | 卡牌数值（cost / reward / theater_asset 在 `entity_types/cards/`） |
| `store.yml` | `price` / `quantity` / 增删条目 | 商品种类（`spec`/`equipment`/`nationality` 要过游戏枚举） |
| `main.yml` | `prestige` / `score` / `card_store` | 抽卡概率（`card_probabilities` 在 L2，只读） |

* **【实证】** 总部经验 `xp` / `xp_target` **不能手改**（派生值，见 §5.14）—— 这是 U94 主动删掉的功能。
* **【实证】** 根 `main.yml` 顶层固定 **17 个键**：`campaign_id` / `campaign_name` / `card_store` /
  `conference_start_state` / `destroyed_cities` / `in_state` / `level` / `milestones` / `num_buyed_turns` /
  `prestige` / `renamed_hqs` / `reverted_games` / `score` / `standalone_scenario` / `tokens` / `tokens_map` /
  `used_card_types_with_unit`。

### 1.5 两套「单位表」：名册 vs 活表

* **【实证】** `document/units.yml` = **战役名册**（历史上出现过的全部单位，含已阵亡，随推进变长），
  只有 4 个字段 `{id, name_brief, name_full, type}`，是 **`type` 的唯一权威源**；
  根 `units.yml` = **当前活着的单位表**（19 字段）。
* **【实证】** 12 个存档实测：**根表 ⊆ 名册**恒成立，反向不成立；
  同 id 的 `name_brief` 完全一致；名册会变长（barbarossa 912→923、west 846→858，多出的是游戏运行时新造的警卫分遣队）。
* **【实证】** `document/scenarios/<场景>/units.yml` **没有 `type` 字段**（只有 10 个字段），
  游戏按 id 去 `document/units.yml` 解析 ⇒ `type` 只能只读展示。
* **对生成器的意义**：战役生成器造新单位 ⇒ 要同时写「名册」与「活表」；`document/` 是只读层 ⇒
  只能靠**改游戏包**（新战役时进 `document/`），不能靠改存档。

### 1.6 单位容器有两种格式（踩过的坑）

* **【实证】** 单位对象字段集在根 `units.yml`、`games/<场景>/units.yml`、`archive/<快照>/units.yml` **完全一致（19 字段）**；
  但**容器有两种格式**：`games/<场景>/units.yml` 可能是 ID 清单 `list[int]`（15/706）或完整对象 `list[dict]`（691/706）；
  根 `units.yml` / `hqs.yml` 永远是完整对象。
* **【实证】** **同一个场景在不同存档里格式可能不同**（9 个场景在部分存档是 `list[int]`）⇒ **每个存档都要重新判类型**。
* **【实证】** 判 YAML 格式要用 `yaml.safe_load`，**别看文本形态**。

### 1.7 二层 ZIP：`games/<场景>/archive` 本身又是一个 ZIP

* **【实证】** 内含逐回合快照目录，命名只有三种形态：`deployment_phase_%02d_%s`、
  `turn_%02d_phase_%02d_%s`（规则来自 `state/game/game.pyc`）。
  实测 12071 个快照目录，文件名并集 22 种，每目录 14–22 个文件。
* **【实证】** `ar_list.yml` 快照里也有（12059/12071），**唯一例外是进行中战斗的最后一个快照没有它**
  ⇒ **不要**用「快照里有没有 `ar_list.yml`」判断回合状态（本项目踩过）。

### 1.8 三层 NumPy 二进制 `.npz`（不用碰）

* **【实证】** `own.npz`（`own`, uint8, **508×373** 阵营控制图）、`fow.npz`（`fow_0`/`fow_1`, bool）、
  `weather.npz`（`weather`, uint8）—— 三者都是 508×373 = 地图六边形格点。
* **限制**：存档修改器**不碰这些**；做引擎改动时若涉及视野/天气/控制图，这是入口。

## 2. 写盘与保真（任何改存档/生成器的红线）

### 2.1 只写 L1 —— 只有两个 L3 例外

* **【实证】** 铁律：L2/L3/L4/L5 一律只读；**文件不存在就禁用对应功能，绝不新建**；**绝不往存档里加任何自定义字段**。
* **【实证】** L3 的两个例外，都只在「**当前进行中战斗**」里：
  1. `theater_assets`（战区资产）—— 写在 `games/<场景>/main.yml` 的**那一个键**，其余键原样搬运（整表替换会丢实时字段当前值）；
  2. **作战标记**（U89 新增）—— `games/<场景>/main.yml` 的三个**单位 id 列表**。
* **【实证】** 历史战斗快照一律不许写。

### 2.2 游戏内回退 = 整表替换（反例：按 id 同步只能改交集）

* **【实证】** 检查点单位集合**比根表少**（实测 conf3：根 138 / `last_conference` 102 / `last_game` 121）
  ⇒ 按 id 同步只能改交集 ⇒ 反而得到「一半新一半旧」的非存档状态。
* **【推断】** 生成器写新单位时，要么同时更新检查点，要么接受「回退后单位消失」。

### 2.3 YAML 序列化必须复刻游戏自己的 dumper

* **【实证】** 游戏规则在 `lib/tools/yaml_.pyc`：`yaml.dump(obj, Dumper=_Dumper, default_flow_style=False)`，
  `_Dumper` 基于 **`yaml.CDumper`** 并注册 5 个 representer：
  1. `list`：元素个数 **1..4**（不是 1..5）且全是标量 ⇒ **流式**（`uv: [354, 215]`）；
  2. `str`：长度 **> 100** ⇒ 块样式 `|`；
  3. `float` ⇒ `str(float(x))`；
  4/5. `bool` / `int` 与默认一致。
* **【实证】** 游戏**没有传 `allow_unicode`** ⇒ 用默认 **False** ⇒ 中文写成 `"1\u7B2C\u82CF\u8054\u8B66\u536B\u961F"`
  （**双引号 + 大写十六进制**）。70 存档 L1 条目里含原始非 ASCII 字节的 **0 个**、含 `\uXXXX` 转义的 **40 个**。
* **【实证】** 复刻后 70 存档 / 337 个 L1 条目「解析 → 重新序列化」**337/337 字节一致**；
  通用 `yaml.safe_dump(allow_unicode=True)` 只有 **281/337**（56 个含中文的条目被整体改写）。
* **【实证】** 短列表门槛写成 `<= 5` 会让 **16 个条目**往返不一致（5 个标量时游戏用块样式）。
* **【实证】** float representer 写错的后果：写成 `represent_float(str(float(data)))` ⇒ PyYAML 内部 `repr()`
  再套一层引号 ⇒ 写出 `!!float "'80.0'"` ⇒ **游戏读这个文件直接崩**。456 处 float **全在 `games/*/main.yml`**，
  根 5 张 L1 表没有 float。
* **【实证】** 读用 libyaml 的 `CSafeLoader`（快 6.6 倍：357ms → 54ms），**写必须用纯 Python 的复刻 dumper**
  （C 版 `CSafeDumper` 输出格式不同）。

### 2.4 重打包要保持游戏的 ZIP 写入约定

* **【实证】** 不写目录条目；所有条目共用一个时间戳；`external_attr = 0x01800000`（= `0o600 << 16`）、
  `create_system = 0`、`compress_type = ZIP_DEFLATED`；**只重写改过的条目，其余条目用原始字节原样复制**；
  解包前先清空工作目录。
* **【实证】** 打包验收口径是「**条目内容逐条 SHA256 一致**」而不是整文件字节一致
  （实测整文件字节级一致 47/70，其余 23 个差约 0.2%，条目内容 70/70 一致）。

### 2.5 写盘管线：备份 → 临时文件 → 校验 → 原子替换

* **【实证】** 顺序固定，一步不能省：
  ① 备份 `<存档名>_BACKUP.usg` → ② **写临时文件**（按原存档条目清单与顺序重建，元数据沿用原存档）
  → ③ 校验（逐条 SHA256 比对，确认只有计划里那几个条目变了）→ ④ **原子替换 `os.replace`**。
  任何一步失败都**完整回滚**，原存档一个字节都不动。
* **【实证】** 写回前必做校验：所有 YAML 能被 `yaml.safe_load` 解析；数值在范围内；可写类型字段在类型表里存在。
* **【实证】** **备份必须是原文件的整体字节拷贝**（不是「重新打包」——重打包会改变条目顺序/时间戳）；
  同名备份已存在时用 `_BACKUP_2.usg`，**绝不覆盖**。

### 2.6 撤销栈：落盘 + 基准校验 + 按 commit 粒度

* **【实证】** 落盘在存档旁边的 `<存档名>.undo.json`（游戏只扫 `*.usg`，不冲突）；
  每条记录存「**改前原始字节**（zlib+base64）」+「**改后 SHA256**」；
  撤销前拿**当前存档内容**算 SHA256 与记录的 `after_sha256` 比对，**对不上就拒绝执行并说明原因，不硬改**。
* **【实证】** 粒度 = 一次 commit（不是一个字段）；撤销走**和 commit 完全相同**的写回管线；
  **拒绝撤销时不能弹栈**；容量上限 **20 条 / 32 MB**，超了从最旧的丢。
* **【实证】** 已知缺口：撤销栈在写盘前就把 `summary` **翻译了** ⇒ 切回中文界面后历史记录仍是英文
  （正确做法是存原文、显示时再翻译）。

### 2.7 游戏 schema 是 `PREVENT_EXTRA` —— 不能加自定义字段

* **【实证】** 游戏用 voluptuous 校验存档 schema，`Schema` 默认 `extra=PREVENT_EXTRA`
  ⇒ 给单位加一个 `'foo_bar'` 键 ⇒ `MultipleInvalid: extra keys not allowed @ data['id']`。
* **【实证】** 校验器**接收携带类型数据库的上下文**（`campaign_data_validation: unit_types ×4, card_types ×3,
  nationality_types ×2`；`hq data_validation: hq_types ×1`）⇒ `unit.type` / `specs[].type` / `card_type` /
  `hq.template` 都通过类型表解析，**写一个不存在的字符串不会得到「未识别类型」而是直接载入失败**。
* **限制**：这些校验函数需要完整 `entity_types` 装载链 ⇒ **别依赖游戏报错兜底，必须自己校验**。

### 2.8 硬约束：数值范围总表（超范围 ⇒ 存档打不开）

| 对象 | 合法范围 |
|---|---|
| 单位 | `xp` **0..400**、`entr` 0..2、`supply` 0..3、`ap` 0..3、`supplied_by` ∈ {0,1,2,3}、`uv` 恰好 2 个非负 int 或 null、`specs` 长度 0..3、`act_st`/`sup_st`/`mp`/`losses`/`retreated` ≥ 0 |
| 商店 | `quantity` **≥ 1**（0 非法）、`price` ≥ 0（0 = 免费商品，正常值） |
| 总部 | `cp` 0..9、`max_cp` 3..9、`supply` 0..3、`trucks` **1..5**（0 不行）、分支 `level`/`suppressed` 各 0..3 且和 ≤ 3、`sp_used` ≤ `sp_avail` ≤2 |
| 战区资产 | `to_use` ≥ 0、`uses_total` ≥ 0 或 `None`（= 无限）、`uses_turn` ≥ 1 |

* **【实证】** 游戏用 voluptuous 校验 ⇒ **超范围 ⇒ 存档直接打不开**（不是「显示异常」）。
* **【实证】** 战力超过 `max_st` 是**软警告**（游戏读档时截回）；特种兵数量超 `min(3, max_spec)` 是**硬拦**。

### 2.9 静默丢数据的坑

* **【实证】** 写回根 `main.yml` 时 **`milestones` 必须原样保留** —— schema 是 `Required('milestones', default=list())`，
  **丢掉这个键不会报错**，会被当成空列表 ⇒ 本局已达成的里程碑与战役奖章**静默消失**。
* **【实证】** 根表其余字段（`card_store`/`tokens`/`tokens_map`/`renamed_hqs`/`reverted_games`/
  `used_card_types_with_unit`）同理：**除非本次明确要改，否则一律原样搬运**。

### 2.10 保真承诺（可直接对外承诺的实测口径）

* **【实证】** 写回时**没改的条目**逐条 SHA256 一致（70 存档 / **52356 条目**全量回归）；
  改过的那一个文件内部没改的行也不动（L1 条目往返 **337/337 字节一致**）。

## 3. 包与 mod 加载机制（改引擎 / 做 mod 重点）

### 3.1 `_packages/` 下面是**包容器**，不是包本身

* **【实证】** 游戏侧 `_packages/base`、`_packages/dlc1`…`dlc10`，用户侧 `_packages/<mod名>/`；
  每个包的数据在 `<包>/data/…`。把容器当包去读 `data/entity_types/` ⇒ **一条类型都读不到**（静默返回 0 条）。

### 3.2 包从哪来：两个容器，用户包在前

* **【实证】** 直接问游戏 `uoc2.paths._Paths` 的输出：
  `all_package_dirs()` = `[%LOCALAPPDATA%\.uoc2\_packages, <game>\_packages]`；
  `all_non_game_package_dirs()` = `[%LOCALAPPDATA%\.uoc2\_packages]`。
* **【实证】** `get_non_editable_packages()` 只含玩家有 Steam 授权的包。

### 3.3 顺序规则（曾经选错包）

* **【实证】** 容器内枚举子目录 = 文件系统 `listdir` **原序**，**不是 sorted**；
  官方包按**数字序**（`dlc2` 在 `dlc10` 之前），不是字母序。
* **【实证】** 用户目录里叫 `base`/`dlcN` 的目录**不算 mod**。

### 3.4 同名文件：第一个包里有的**整文件**胜出 ⇒ mod 替换原版

* **【实证】** `paths.pyc::join_abs` / `get_yml(path)`：包里已有该文件就直接用，后面的包不再参与；
  **不是字段级 merge**。

### 3.5 `packages.yml` 的两个键

* **【实证】** `addable` = mod 允许**新增**的路径，实测为 `data/maps/*`、`data/scenarios/*`、`data/campaigns/*`。
* **【实证】** `not_moddable` 列出的文件（`data/entity_types/nationalities.yml`、`factions.yml`、`shaders/*.yml`、
  `assets/atlases/*` 等）只要在 mod 包里出现 ⇒ **整个 mod 包被禁用**（不是只跳过那个文件）。
  游戏**只在 mod 目录里查** ⇒ **官方包永远不禁用**。
* **【待验证】** 文档未给出 `packages.yml` 的完整条目清单。

### 3.6 创意工坊：只是**分发渠道**，游戏不会自动读

* **【实证】** `init_packages(mod_packages=())` 默认空，全 lib 无人调用 ⇒ 标准启动**不加载**创意工坊包。
  `edit_ctrl.pyc::_update_workshop_item` ⇒ `set_item_content_dir(self._package_path)` ⇒ 下载到的是**包的裸文件**。
* **【实证】** UoC2 的创意工坊 mod **不自动安装**（作者自己写明「订阅 ≠ 安装完成」）⇒
  「已下载但没解压进游戏目录」是常态 ⇒ 读创意工坊目录是必读项。

### 3.7 创意工坊 mod 的三种形态 + 读取优先级

* **【实证】** ① **裸文件**（`<项目>/data/entity_types/…`，项目目录本身就是一个包）；
  ② `dir`（`<项目>/_packages/<包名>/…`）；③ `zip`（`<项目>/xxx.zip` 里的上面两种，**只读不落盘**）。
* **【实证】** 优先级 = **磁盘包（用户包 → 官方包）优先**，创意工坊包**只补空缺**
  ⇒ 游戏真正在用的数据不会被「还没装进游戏的 mod」盖掉，但创意工坊 mod 提供的**新**类型会被读到。
* **【实证】** 存档里的 `document/` 已经是 **mod 生效后**的版本 ⇒ 玩家事后升级/卸载 mod **不影响已有存档**。

### 3.8 `.patch.yml` 增量机制（钉死了机制，没钉死合并语义）

* **【实证】** `paths.pyc::get_yml` 的逻辑是**先找整文件，找不到就找 `<同名>.patch.yml`，补丁可以叠加**。

### 3.9 普通 mod vs 改游戏引擎的 mod

## 4. 战役 / 会议 / 场景系统（战役生成器重点）

### 4.1 三级结构与包里的文件布局

* **【实证】** 战役包 = `<战役>.usc/{cinematics,conferences,fronts,scenarios}`；
  会议同时以两种形式存在：**公共会议文件** `conferences/c_XX_YY.yml`（只有 `card_probabilities/date/period`）
  与**战线内会议文件** `fronts/<战线>/conferences/<conf>.yml`
  （有 `store/elite_store/card_probability_scales/tracks`）。
* **【实证】** `fronts/<战线>/segments/` **是空的**；`tracks` 推不出场景
  （`default_segment` 是段名如 `s_44_05_italy`，不是场景名；`tokens` 只在部分会议出现；`alternatives` 是互斥分支）
  ⇒ **「会议→可选场景」只能靠内置索引**。

### 4.2 id 形态

* **【实证】** 战役 id = 包名（`west` / `stalingrad`…，1:1 对应一个 `.usc`）；
  会议 id 形如 `c_43_04`（也有 `c_01`、`c_03_dummy`）；战线 id = 目录名（`italy`/`south`/`caucasus`/`france`/`north`/`eur`…）；
  场景 id = 场景目录名；场景另有 `variant` = `base` / `variant`。
* **【实证】** 140 个会议 id 的形态分布：`c_NN_NN` ×103、`c_NN` ×35、`c_NN_word` ×2；
  386 个场景：`variant` ×104、`base` ×282。
* **【待验证】** `c_XX_YY` 两段数字各自的语义**没有定论** —— 不要自行赋予含义。
* **【实证】** 场景 id **不全局唯一**：`normandy_breakout` 同时在 base 的 `france.usc` 和 `west.usc` 里。

### 4.3 14 个战役包与 5 种路线 id

* **【实证】** 游戏包共 14 个战役包 = base 3（france/tutorial/west）+ dlc1–dlc10 共 11 个；
  内置索引含 14 个战役，每个带 1–3 条路线，路线 id 只有 5 种：`historical` / `fantasy` / `relief` / `cairo` / `aida`。
* **【实证】** 映射：base = `france`,`west`；dlc1 `blitzkrieg`、dlc2 `barbarossa`、dlc3 `moscow`、dlc4 `stalingrad`、
  dlc5 `don`、dlc6 `desert`、dlc7 `fox`、dlc8 `kursk`+`zitadelle`、dlc9 `balaton`+`berlin`、dlc10 `ardennes`。
* **【实证】** 路线（historical/fantasy/…）是**版本化的静态规划投影**，**游戏包里没有这个概念**
  ⇒ **不是玩家实际走过的路线**。
* **【待验证】** base 包里的 `tutorial` 战役不在索引 14 个之列，理由未记录。

### 4.4 内置索引 `campaign_index.json`

* **【实证】** schema `uoc2-campaign-index/v1`，只存「会议→可选场景」一层；
  结构 = `campaigns.<战役id>.{name, packages[], routes.<路线>.meetings[].{id, text, scenes[].{id, variant, name}}}`；
  体积 33.5 KB，覆盖 14 战役 / 140 会议 / 386 场景。
* **【实证】** 索引缺失时返回空索引，**不报错**（降级成「没有会议→场景列表」）。

### 4.5 路线选择：历史线优先（U66）

* **【实证】** 判定对象是**关卡（scenario）**而不是会议；优先级：
  ① 关卡在历史线里 ⇒ 走历史线；② 历史线没有 ⇒ 去别的路线找这个关卡，取找到的第一个；
  ③ 都不是（存档不在战斗中）⇒ 退回按会议找，再不行用第一条（历史线）。
* **【实证】** 根因是旧实现用 `routes()` = **sorted** ⇒ `"fantasy" < "historical"` ⇒ 幻想线永远先命中；
  **数据本身没错**（索引三条线与研究包 `conclusion-package/conclusions/stalingrad-campaign-{historical,fantasy}-v1.json`
  **逐场景完全一致**）。

### 4.6 存档里「当前在哪场会议 / 哪个场景」怎么定位

* **【实证】** 全部判据来自存档**根 `main.yml`（L1）**：`campaign_id` +
  `in_state.{conference, front, scenario, variant}`；激活战线来自 `store.yml` 的**顶层键**；
  `in_state.scenario` 非空 ⇔ 正在战斗中。
* **【实证】** `in_state` 字段全集 = `completed / conference / front / fronts / lost_scenario / scenario /
  segment_finished / variant`；70 存档中 **69 个能完整定位**，另 3 个是独立场景存档。
* **【实证】** `in_state.front` 与 `in_state.scenario` **完全等价**；`in_state.variant` 战役 2/67 非空。
* **【实证】** `games/<场景>/main.yml` **没有** `scenario` 字段 ⇒ 已结束战斗的场景名只能从目录名取。

### 4.7 场景名册（roster）的来源与结构

* **【实证】** 来自**游戏包默认配置**（不是玩家存档），4 个文件：
  `scenarios/<id>/units.yml`（27–39 单位）+ `hqs.yml`（4–5 HQ）+ `main.yml`
  （`map_name`/`start`/`base_num_turns`/`turn_seq`/`theater_assets`）+ `locale.yml`（场景名是 locale 键，363/363 = 100%）。
* **【实证】** 场景 `units.yml` 的单位**只有 `name_brief`，没有 `equipment`/`type`** ⇒ 推不出单位类型、拿不到单位头像；
  只有 `specs[].type` 有 ⇒ 名册行不画单位头像。
* **【实证】** 名册**不保证**单位存活 / 继承 / 登场。

### 4.8 会议商店：两档 + 存档覆盖包默认

* **【实证】** 包默认商店在 `fronts/<战线>/conferences/<会议>.yml`，顶层键
  `{card_probability_scales, elite_store, store, tracks}`；存档侧 `store.yml` = `{战线: {store: [...], elite_store: [...]}}`（**两层**）。
* **【实证】** 存档商店**覆盖**包默认（`conference.set_store_data(存档)`）⇒ 包默认 ≠ 玩家当前库存。
* **【实证】** 5/5 战役包的全部会议文件 `elite_store` **恒为 `null`**。
* **【实证】** 条目形态**只有两种**：`{equipment, nationality, price, quantity}`（`equipment` ∈ `infantry`/`armor`）
  或 `{spec, nationality, price, quantity}` ⇒ `spec` 与 `equipment` **二选一**（同时写两个、或写第三个键都会被 PREVENT_EXTRA 拒）。

### 4.9 商店条目语义与「买空」机制

* **【实证】** `price` = 单价（`price: 0` 是**游戏正常产生的免费商品**，70 存档里 43 条）；
  `quantity` = 剩余可买数量；**游戏里没有「已售罄」标记** —— 装备类买后条目保留、`quantity` 递减，
  特种兵类买后**整条消失**。
* **【实证】** 70 存档 1659 条商店条目里 `quantity: 0` 的**一条都没有** ⇒ 造 `quantity: 0` = 造出游戏从不产生的状态。
* **【实证】** 商店顶层键必须是游戏包 `fronts/` 的**子集**（= 当前已激活战线），**不要凭空新建战线键**。
* **【待验证】** 存档价格与包静态清单不一致（south 战线 3 条被上调）—— **原因未定位**，
  ⇒ **不要拿游戏包去「纠正」存档**。

### 4.10 重复条目规则（只拦新增，不校验存量）

* **【实证】** 身份 = `(商品类型, 国籍)`（**国籍算进身份**）；价格/库存不同也算重复。
* **【实证】** 商店：同一个 `(front, sub)` 内已有同身份 ⇒ 硬拦（不跨战线判）；
  兵库：该总部已有**同身份 + 同延迟** ⇒ 硬拦（延迟不同可共存）。
* **【实证】** 存量重复**都是游戏自己生成的**（商店 1696 条中同身份重复 23 组、完全相同 0 组；
  兵库 3018 条中同身份重复 696 组、其中完全相同 393 组）⇒ 别按「数据里有重复」就以为判重规则错。

### 4.11 兵库（force_pool）：字段、延迟语义、合并键

* **【实证】** 条目 = `{delay, nationality, quantity, spec|equipment}`；游戏对 HQ 兵库**恒为延迟制**
  （`hq.pyc` 第 119 行 `ForcePool(gamelike, force_pool, True)`）⇒ 条目带 `delay` **不带** `price`。
* **【实证】** 游戏的合并键 = **`(delay, nationality, spec / equipment)`** —— 加同键条目是
  `fp.quantity += quantity` **合并**，不是并存；`deploy_with_delay(delay)` 只取 `fp.delay == delay` 的条目，逐批部署。
* **【实证】** 延迟实测分布：`0`×2800 / `1`×68 / `2`×72 / `3`×47 / `4`×26 / `5`×4 / `10`×1。
* **【实证】** `delay` 必须**非负整数**（游戏 `force_pool_schema` 硬要求）⇒ **负数会让存档打不开**。
* **【实证】** 特种兵条目的国籍**自动跟随类型**（1747 条 spec 0 例外）；装备条目只有 `infantry`/`armor` **类别**、无数值。
* **【实证】** 兵库条目身份**只能用存档原始下标**定位（真实存档 696 组同身份重复、393 组完全相同）
  ⇒ 删除类编辑必须按 index **降序**执行；**界面行号 ≠ 存档下标**。

### 4.12 手牌 vs 货架（曾经命名反了）

| | 来源 | 是什么 | 上限 |
|---|---|---|---|
| **手牌** | 根 `cards.yml` | 已经拿到手里的牌 | `card_deck_limit`（easy/normal 5、classic 4、hard 3） |
| **货架** | 根 `main.yml.card_store` | 会议界面里可以买的牌 | `card_store_limit`（恒为 5） |

* **【实证】** 游戏侧 `BuyCard.do` = `card_store.pop(position)` → `campaign.add_card(...)`。
* **【实证】** 旁证：实测存档手牌正好 **4** 张、货架正好 **5** 张。
* **【实证】** ⚠️ **口径冲突**：`docs/开发规范与Prompt.md:1634-1637` 的措辞与上表**相反**
  ⇒ 以游戏字节码（`BuyCard` 从 `card_store` 弹出进手牌）为准。
* **【实证】** `card_store` 为空**不能**推断「没有卡牌商店」（取样时不在会议阶段）。

### 4.13 `is_free` 在两处的语义完全不同

* **货架**：`is_free=True` ⇒ 价格 **0**（不扣声望）⇒ 改免费 = 白嫖。
* **手牌**：**没有任何玩法影响** —— 只改 tooltip 文案（`id_tooltip_deck_card_free`/`_paid`）与卡背贴图
  （`face_down_free`/`face_down`）。
* **【实证】** 游戏里免费卡数由难度定（`card_store_free_cards`），**手动改的要标注「手动改的」**。

### 4.14 会议卡牌的生成机制与上架白名单

* **【实证】** 进入会议时 `set_conference()` → `create_random_card_data(card_store_limit[level], all_free=False)`：
  权重 = 全局基础表 **15/6/3 三档** → 公共会议文件 `card_probabilities` 覆盖 →
  各前线 `card_probability_scales` 缩放（空 dict = 该层不覆盖）；前 `card_store_free_cards[level]` 张标 `is_free=True`。
* **【实证】** 常量（`constants.pyc`，easy/normal/classic/hard）：
  `card_store_limit` = 5/5/5/5、`card_store_free_cards` = 2/1/0/0、`card_deck_limit` = 5/5/4/3。
* **【实证】** `Campaign.load` 直接读存档 `card_store`，**加载时不重掷**；重掷只发生在进入**新**会议时
  ⇒ 货架可改，但只管这一场。`card_probabilities` 在 L2 **只读** ⇒ 抽卡概率不可改。
* **【实证】** 可上架白名单 = 逐条复刻 `Campaign.get_cards_probabilities`：
  ① `card.faction == player_faction`；② 该卡 `meta_type` 在本次会议概率表里 **> 0**；
  ③ `has_unit` 的卡还必须登记在 `document/main.yml.card_type_units`、不在 `used_card_types_with_unit`、
  不在手牌里、预留单位未被消耗。
* **【实证】** 白名单是「**当前存档 + 当前会议**」的状态 ⇒ **每次重算，别缓存**；
  核心库写盘前还要再校验一遍。
* **【实证】** 带单位的卡 `unit_id` 必须**等于** `card_type_units[card_type].unit_id`
  （不是「名册里任意一个单位」）⇒ 给错会召唤出错误单位、给 `None` 则**用卡时游戏崩**。
* **【实证】** 登陆/空降卡会召唤单位；战役里没有这个单位 ⇒ 硬写进去 ⇒ 买的时候 `unit_id` 为空 ⇒ 卡进手牌却没有单位。

### 4.15 难度字段与手牌上限

* **【实证】** 难度存于存档**根 `main.yml` 的 `level`**；
  `campaign_schema` = `Required('level', default='normal'): In(play_levels)`，
  `play_levels = ('easy','normal','classic','hard')`。
* **【实证】** 难度还决定：以后新会议的免费卡数 / 折扣卡数 / AI 强度 / 「重置会议」时重建的 HQ 卡车与步兵阶梯。
* **【实证】** 实测 70 存档难度分布：战役 classic 38 / hard 29；独立场景 3/3 classic。

### 4.16 总部经验目标 `xp_target` 的完整公式

```
xp_target = ceil5( n × num_turns × f )
```

* `n` = 该总部在「**所有战线、当前会议段的所有场景预设**里出现过的**不同单位数**」
* `num_turns` = 这些场景的 `base_num_turns` 之和（**只统计当前段**）
* `f` = `hq_xp_taget_fudge_factor`（**游戏里拼错成 `taget`**），位于 `_packages/base/config/game.yml`，
  **默认 0.75，教学战役覆盖成 7.5**
* `ceil5` = 向上取整到 **5 的倍数**
* **【实证】** 字节码：`state/campaign/campaign.pyc::Campaign._set_hqs_xp_target`（源文件 1788–1817 行）；
  同函数里还有 `hq.xp = hq.xp % hq.xp_target` ⇒ **玩家经验永远 < 目标**（8 个存档 100% 满足）。
* **【实证】** 只算 `persistent` 总部（临时总部走 else 分支 ⇒ `xp_target=0, xp=0`）；
  `n` 取**预设里的单位数**，不是存档里活着的单位数 ⇒ **玩家打掉单位不会降低需求**；
  **只在战役推进时算** ⇒ 存档里的值是上次推进时的旧值。
* **【实证】** 实测逐字吻合：west 的 hq5（n=6）⇒110、hq13（n=11）⇒200；
  Stalingrad 的 hq1⇒220、hq2⇒350、hq11⇒220、hq14⇒155、hq16⇒90。
* **对生成器的意义**：**做战役生成器时必须自己算这个值**（否则总部的经验进度会错）；
  校验工具现成：`tools/verify_hq_xp_target.py`（只读，逐个总部对比）。

### 4.17 战役常量（`document/main.yml`，生成器要读的）

* **【实证】** 含 `prestige`(100)、`score`(0)、`player_faction`('allies')、`win_conference`('c_45_06')、
  `milestones`（23 个，每个 `{do_not_take, name_brief, scenario_name, objective}`）、`persistent_hqs`、
  `hq_renames`、`card_type_units`（卡牌类型 → `{unit_id, replacement_unit_id}`）、`branching_token_char`。
* **【实证】** `milestones` 中 `success_90` 标记 `do_not_take=True`（UI 不提供勾选）。

### 4.18 生成器会撞到的三条硬约束

* **【实证】** ① `xp`/`xp_target` **不能手改**（派生值）；
  ② `milestones` **没有对应 Edit**；
  ③ 「跳到某会议」**没有这种 Edit** —— 游戏只提供 `set_conference(conference, save_revert_data)`，
  走 `last_conference/` 写盘。
* **【实证】** 每次存档 `games/<场景>/` 会被**整个删除并重写**。

## 5. 游戏运行时行为（改引擎重点）

### 5.1 读档时的自动修复（目前钉死了三处）

| 字段 | 行为 | 依据 |
|---|---|---|
| 单位 `act_st` / `sup_st` | 各截到该单位 `max_st`，且 `act_st + sup_st` 压到 ≤ `max_st` | `UnitState._repair_data`（`unit.pyc:200` 附近） |
| 总部 `cp` | 超过 `max_cp` 时截回 | `HQState._repair_data`（用捕获 `max_cp` 的 lambda） |
| （其余字段） | **未成表** | 【待验证】 |

* **【实证】** `max_st` **不在存档里**（所有用户存档 `units.yml` 里 0 处 `max_st`）⇒ 截回值由**类型表**决定。
* **【待验证】** 完整字段清单未做出来 —— 做引擎改动时建议先反汇编 `UnitState._repair_data` /
  `HQState._repair_data` 出一张完整表。

### 5.2 兵力上限 `max_st` 的口径（最容易搞错的一条）

* **【实证】** `max_st` **按类型各按各的**：627 个类型的取值 = `[3,4,5,6,7]`
  （分布 `3×4 / 4×9 / 5×83 / 6×108 / 7×245`，另有 **178 个类型没写该字段**）。
* **【实证】** 类型 yml 没写 `max_st` 时，游戏 schema 按 **7** 处理
  （`Required('max_st', default=7): All(int, Range(min=1, max=7))`）⇒ 读 yml 拿到 `None` 要回填 7。
* **【实证】** `max_st` 约束的是**普通部队**（`act_st` + `sup_st`）⇒ **特种兵不占名额**。
* **【实证】** **总战力超上限游戏允许**：真实存档 1430 个单位里有 **166 个**总战力超上限（最多超 3 点）
  ⇒ 「7 兵 + 2 特种兵」是合法的。
* **【实证】** 游戏自己加兵也按这个口径：`UnitState.add_act_st` 用 `min(..., max_st, tot_st)`、
  `can_use_deploy_step` 用 `tot_st < max_st`。
* **【待验证】** `tot_st` 的定义**未定位到代码对象**，按语义推断为 `act_st + sup_st`。

### 5.3 特种兵「被压制」= 存档里的 `active` 字段

* **【实证】** `SpecialistState.__init__(gamelike, type, active, captured, idx)` —— 只有 4 个字段，
  **不存在独立的 suppressed 字段**；`active=false` **就是**被压制。
* **【实证】** 渲染按 `active` 选图（`status_act` / `status_sup`）；
  火力压制时置 `active=False`（`apply_losses_att_pindown`）；按恢复步数逐步恢复（`apply_recovery_specs`）。
* **【实证】** 这是**持久状态** —— 真实存档里本来就有 15 个 `active=false` 的特种兵，是游戏自己压出来的。

### 5.4 工事等级 / 移动力 / 行动力

* **【实证】** `entr` = 工事等级（上限 **2**）；`mp` = **剩余**移动点（**状态量**）；
  `ap` = 行动力（四档：`ap_none=0 / ap_conv=1 / ap_lock=2 / ap_full=3`，`ap_max_value = 3`）。
* **【实证】** `mp` 由 `apply_mp_ap` 每次重算：有补给给满 `_type.move`、没补给扣一点；
  攻击后 `ap_full → ap_lock`；摩托化（`MotorPool`）在 `ap == ap_conv` 时把 AP 换成移动力。
* **【实证】** 移动力上限 = 类型的基础移动力（`us_arm_42` = 5、步兵 `us_inf_42` = 3）。
* **【实证】** 生命周期：**战斗中改立即生效**（直到下个回合开始）；**战斗外改**进战斗后回合开始会被重算
  （`entr` 不受影响）。

### 5.5 敌方控制区（ZOC）：没有「锁定字段」，只有 `mp=0` + AP 降级

* **【实证】** 进入控制区那一刻，游戏置 `_new_mp = 0`，并把 AP 降级（`ap_none` 或 `ap_lock`），
  随后 `_apply_unit_move` 把 `mp`/`ap` **写回单位并持久化** ⇒ **不存在独立的「锁定移动」字段**。
* **【实证】** 整个存档（战役层 + 战斗层 + 场景层）递归扫过，含 lock / zone / frozen / stuck /
  immobile / pinned / halt / can_move / zoc 之类字样的键**零命中**。
* **【实证】** 界面显示的移动力每回合重算 ⇒ **「看着还有移动力」是显示层重算造成的假象**。
* **【实证】** 实测佐证（`west.usg` 的美国第一装甲师进控制区并打过一仗）：
  `act_st 5→4`、`sup_st 0→1`、`xp 220→225`、`ap 3→0`、`mp 5→0`。
* **【实证】** 官方规则文本吻合（locale `id_super_tooltip_sheet_items_movement_legend_zoc`：
  「进入控制区域的单位在回合剩余时间内会被"锁定"：它也许还能攻击，但无法进一步移动」）。
* **【实证】** 已**撤回**「起点终点都在控制区 ⇒ 成本 = 不可通行」那条结论（实测不阻止从控制区走出）。

### 5.6 作战标记（不能撤退 / 后卫部队 / 反击）

* **【实证】** 三个标记是战斗层 `games/<场景>/main.yml` 里的**单位 id 列表**：
  `no_retreat_units` / `rearguard_units` / `elastic_defense_units`。
* **【实证】** **三个标记互斥 —— 一个单位同时只能有一个**（U102）：
  ① `Gamelike.has_any_defense_flag`（`gamelike.pyc:1452-1455`）= 在三个列表**任意一个**里；
  ② 三个 `can_make_*`（`entities_view/unit.pyc:84/91/98`）的最后一个条件都是
  `not has_any_defense_flag(self.id)`；
  ③ `UnitSetFlags._set_flags`（`scenario/commands_unit.pyc:359-368`）
  = 先从三个列表全 discard、再 add 进**其中一个**；
  ④ `get_defense_flag_string`（`gamelike.pyc:1470-1476`）**只返回一个**
  ⇒ 存档里有冲突时游戏只认第一个（优先级 no_retreat → rearguard → elastic_defense），
  其余**静默忽略**。
* **【实证】** 它们是 **HQ 技能下的「命令」**，**敌方下一回合结束前有效**，游戏回合开始会清
  （`Game.start_turn_clear`）⇒ **只对当前回合有效**。
* **【实证】** 「反击」只能挂**装甲机动单位**：判定式 = `armor and not armor_def and movement == 'mobile'`
  （`state/entities_view/unit.py:45` 的 `armor_mobile`），且 `can_make_elastic_defense`（:98）的
  **第一个条件**就是它；「死守」「后卫部队」**没有**这条限制。
* **【实证】** `armor_def` = **防御装甲** ⇒ 步兵（`armor:1` 但 `armor_def:true`）与
  摩托化步兵（42 个类型 `movement=mobile` 但 `armor_def=true`）**都不算**。
* **【实证】** `HQState.can_unit_elastic_defense` = CP 够 + 单位在 HQ 范围内 + `unit.can_make_elastic_defense()`。
* **【实证】** 名称走 locale（`id_no_retreat` / `id_rearguard` / `id_elastic_defense`）；
  图标在 `assets/surfaces/sheet/special_defense_<key>.png`。
* **教训**：实现任何「游戏里有这个概念」的功能，都必须把游戏的 `can_make_*` 判定链找出来，
  不能只看数据长什么样（U89 一开始只按「存档里有这个列表」实现，漏了挂载前的类型检查）。

### 5.7 派生值清单（游戏会重算 ⇒ 手写无效）

| 字段 | 谁重算 | 时机 |
|---|---|---|
| `hq.xp_target` | `Campaign._set_hqs_xp_target` | **战役推进**时（公式见 §4.16） |
| `hq.xp` | 同上（`xp %= xp_target`） | 战役推进时 |
| 单位 `mp` / `ap` | `apply_mp_ap` | 每个回合开始（战斗外改会被重置） |
| 战区资产 `to_use` | `Game.new`（`to_use = uses_turn`） | 开新战斗时（**读档不重置**） |
| 场景预设单位 `type`/`supply`/`sup_st`/`specs.active` | `Game.new` 的重组 | **只有**「点开始这场战斗」这条路径 |
| 登陆/空降/早期增援的 XP | `deploy_calc_new_xp = max(100, xp - steps × cost)` | 同上 |
| 总部分支 `suppressed` | `unsuppress_branch_levels` | **一局结束时**全部还原 |
| 总部 `force_pool` 的 `quantity` | **从不重算** | —— |
| 卡牌货架 `card_store` | `set_conference` 时重掷 | 进入**新**会议时（读档不重掷） |

* **【实证】** 重组只发生在 `Game.new`（玩家点「开始这场战斗」那一刻），**读档继续战斗不重算**
  （`Game._load`）；安全边界是「**这场战斗已经开始**」，不是「战役已经开始」。
* **【实证】** ✅ **但 `xp` / `act_st` / `specs` 列表 / 改名对「场景预设单位」是战斗外也生效的**
  ⇒ 「提前强化」不需要一场一场打。

### 5.8 `sp_used` 与 `cost` 是一对

* **【实证】** 存档 `branches[分支][i].cost` 存的是**已经扣掉专精减免**的 CP 消耗
  ⇒ 原始 CP = `cost + sp_used`；只写 `sp_used` 不动 `cost` ⇒ 存档自相矛盾。
* **【实证】** `sp_avail` 上限 ≤2；兵库四动作 + `motor_pool` **没有技能点**（`sp_avail = null`）；
  **`intel` 分支恒为空**（455/455 总部）⇒ 情报没有技能。
* **【实证】** 专精 = 该技能发动时 CP 消耗 −1。

### 5.9 分支压制语义：`suppressed` 是**级数**，不是布尔开关

* **【实证】** `branch_levels[分支] = {level, suppressed}` —— `level` = 当前**生效**等级（0–3），
  `suppressed` = **被压住的级数**（整数 0–3）；游戏内部「解锁到几级」= `level + suppressed`。
* **【实证】** `branch_suppress` = 生效等级 −N、被压数 +N（**真实等级不变**）；
  `branch_actions` = **生效看 `level`**、解锁看 `level + suppressed`。
* **【实证】** 压制只在「战役进行中」的存档里有值（`set_end_game` 会还原它）。

### 5.10 总部补给卡车 `trucks` 的 1-based 陷阱

* **【实证】** `trucks` 是整数，存档里**没有 0**（实测 1467 个总部分布 `{1:119, 2:897, 3:428, 5:23}`）；
  1–5 辆 ⇒ 补给作用范围 **5 / 8 / 10 / 11 / 12** 格（`config/game.yml` → `supply_hubs_ranges`）。
* **【实证】** ⚠️ 字节码 `HQState/mp_movement` 用 **0-based** `supply_hubs_ranges[self.trucks]`
  ⇒ **比游戏内 UI 标签少一格**（游戏 UI 是 1-based）。

### 5.11 战区资产

* **【实证】** 候选全集 **7 种**（`air_supply`/`air_attack`/`saturation_strike`/`long_range_recon`/
  `naval_bombardment`/`flying_artillery`/`precision_bombing`）；场景定义 3 字段，运行时 5 字段；
  `theater_assets` **恒为 2 个 phase 组**（实测 730/730 战斗文件恒 2 组、2320/2320 项恒 5 字段）。
* **【实证】** `uses_total = None` 表示**无限**（不是「不改」）；无限时每回合 `to_use = uses_turn`、**不累积**。
* **【实证】** 唯一的崩溃点与无限/有限无关：**有限时 `to_use > uses_total` ⇒ `uses_total` 变负 ⇒ 存档打不开**。
* **【实证】** 卡牌里的 `theater_asset` 是**另一套**名单（10 个一次性能力 + 这 7 种），
  那 10 个**不能**进战区资产列表（游戏 schema 会拒）。

### 5.12 改名可以写明文（不需要 temp mod）

* **【实证】** `is_str_id` 只认 `id_`/`idp_` ⇒ **明文原样返回**；
  游戏包原件 12061 条单位里就有 24 条非 id 名；70 存档的 84462 条单位条目里有 **746 条明文 `name_brief`**
  ⇒ 游戏自己就在写明文 ⇒ 直接写 `name_brief`/`name_full` 即可生效，**不需要重启游戏、不需要写任何 temp mod**。
* **【实证】** 改名只改根表就够（名字流向是「运行时对象 → 名册」）。

### 5.13 贴图与资源命名规则

* **【实证】** 贴图在 `<游戏安装目录>\_packages\base\assets\surfaces\`（约 180 MB，**绝不打包**）。
* **【实证】** 命名：单位头像 `unit/<type>/sheet_L.png`（**大小写不敏感**）→ 退 `sheet_R.png` → 占位；
  战力阶梯 `steps/step[_<equipment>_<equipment_q>].png`；特种兵 `specialist/<type>/hq_action_icon.png`（160×160）；
  总部技能 `hq_upgrade/hq_upgrade_<action>_{off,on}.png`；卡车 `hq_upgrade/truck_<N>_{on,off,hover}.png`（180×140，档位数字画在贴图里）；
  战区资产 `theater/<asset>_neutral.png`。
* **【实证】** 路径必须照真实目录写 —— `unit/ger_arm_42/` **不存在**（德国 42 年装甲是坦克 `ger_pz_42`）⇒ 引用即空白图。
* **【实证】** 卡牌贴图文件名 **≠** `image` 字段：`image: cards/air_attack_allies` → `bgt_air_attack_allies.png`；
  `sabotage_allies` → `bgm_sabotage.png`（**去阵营后缀**）；`generic_para` → `logo_divisional_para_allies_1.png`（**类型名兜底**）。
  查找顺序：`bgt_/bgmf_/bgm_/logo_` + 原名 → 原名 → 去阵营后缀 → 类型名兜底 → 占位（实测 39/39 全命中）。

### 5.14 静态表只做「候选」，绝不做「白名单」

* **【实证】** 内置表/overlay 过期时不得把玩家锁死 —— 下拉里没有的特种兵**允许手输 type id**；
  校验 `max_spec` 时表里查不到 ⇒ **只提示、不拦截**；存档里出现表里没有的 `type` ⇒ 照常显示，不抛异常。
* **对生成器的意义**：静态表会过期（游戏更新、新 DLC、mod）⇒ 内置索引要有「缺失即降级」的路径。

### 5.15 软警告的判定规矩（做引擎时的通用教训）

* **【实证】** 同一批编辑是**依次执行**的 ⇒ 任何「两个字段互相影响」的判定**不能看中间态**。
  （U96 的兵力上限误报就是这么来的：先执行 `act_st` 时 `sup_st` 还是旧值。）
* **【实证】** 写入时**自动配平**是标准做法：改 `act_st`/`sup_st` 后若「活跃 + 压制」超过 `max_st`
  ⇒ 先从压制里扣，不够再截活跃，口径与前端夹取、与游戏读档修复一致。
* **【实证】** 字段一旦不让改了，**连它的警告一起删**（死代码比没有更糟）。
